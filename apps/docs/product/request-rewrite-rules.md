# 请求重写规则设计

> **状态：已实现，本文对齐当前代码实现。**
>
> 本文描述当前仓库中已经落地的“请求重写规则”能力，包括数据库表、管理 API、前端页面、代理执行和观测行为。文中凡标注“后续”或“待讨论”的部分，表示当前实现尚未覆盖。

## 1. 背景与目标

OSW 当前主要负责协议识别、ProviderModel 路由、故障切换、协议转换和请求观测。实际使用中，不同供应商或模型之间存在大量轻量兼容差异，例如：

- 需要修改或补充 `User-Agent`；
- 需要增删或重写请求 Header；
- 需要修改请求 JSON 中的供应商私有字段；
- 需要调整 thinking/reasoning 相关字段；
- 需要在响应返回客户端前修正某些 JSON 字段。

当前实现提供一条**可配置、可排序、可复用、可观测的重写规则链**：

1. 请求重写规则作为独立一级配置实体，在控制台中集中管理；
2. ProviderModel 可以选择适用的规则并调整执行顺序；
3. 重写动作按报文阶段执行，区分请求阶段和响应阶段；
4. 请求详情可以展示上游请求、上游响应和转换后的正文内容，规则执行摘要目前仅记录规则 ID 列表；
5. 每条规则只做小而明确的修改，规则失败有确定的错误语义；
6. 默认不泄露密钥和完整敏感正文；脚本动作是结构化配置的补充（处理「一条规则要按内容改多处」这类结构化动作拼不出来的情况），不是默认首选。

## 2. 非目标

当前实现仍不包含以下内容：

- 脚本动作以外的任意代码执行入口；
- 复杂表达式语言、网络访问、文件访问或进程调用（脚本动作也在同一套限制下，见 §5.5）；
- 根据规则修改路由关键字段、ProviderModel 候选集合或故障切换策略；
- 规则的全局继承、模型覆盖、端点覆盖多级合并；
- 首期完整支持流式响应 Body 的任意重写；
- 规则版本回滚、发布审批和多用户权限管理；
- 通过规则保存完整请求/响应样本。

## 3. 核心术语

| 术语 | 定义 |
| --- | --- |
| 请求修改 | 全局管理的可复用规则实体，名称在实现中为 request rewrite rule |
| 动作 | 规则执行时对 Header 或 JSON Body 进行的一次具体修改，动作自带请求/响应阶段 |
| 规则链 | 某个 ProviderModel 绑定的有序规则集合 |
| 客户端原始请求 | 客户端发送的原始请求，只采集和展示，不由修改器修改 |
| 请求修改器 | 在协议转换完成后、发送到真实 Provider 前修改 upstream 协议形态的请求 |
| 响应修改器 | 在真实 Provider 响应完成后、对非流式响应做反向转换前或转换过程中的最终 JSON 结果进行修改 |
| attempt | 一次具体的 ProviderModel 尝试；故障切换到下一个模型时重新执行规则链 |
| 规则快照 | 某次 attempt 开始时读取的、不可变的启用规则及绑定顺序 |

## 4. 执行语义

### 4.1 推荐管线位置

规则必须明确作用于哪一种协议形态，避免同一个字段在客户端协议、上游协议和转换中间态之间产生歧义。首期推荐在协议转换边界之外执行：

```text
客户端原始请求
  → 协议转换（客户端协议 → upstream 协议）
  → 请求修改器
  → 发送真实 Provider
  → Provider 原始响应
  → 协议转换（upstream 协议 → 客户端协议）
  → 响应修改器
  → 返回客户端
```

修改器始终位于协议转换器之后：请求修改器处理转换后的 upstream 请求，响应修改器处理反向转换后的 client 响应。修改器不处理客户端原始请求、Provider 原始响应，也不处理协议转换器内部的中间报文。规则阶段统一为 `request` 或 `response`，每个阶段的规则只能看到对应的最终协议形态。

### 4.2 每个 attempt 独立执行

规则链在每个 upstream attempt 上独立执行：

```text
attempt 1：构造上游请求 → 执行规则 → 发送
attempt 1 失败
attempt 2：重新构造上游请求 → 执行规则 → 发送
```

不得复用上一次 attempt 已修改的 Buffer、Header 或 JSON 对象，避免规则叠加、跨供应商污染和故障切换后的错误请求。

### 4.3 规则顺序

规则顺序主要来自 ProviderModel 绑定关系；全局规则按创建时间排序后与绑定规则拼接执行：

- 同一规则可以被多个 ProviderModel 复用；
- 不同 ProviderModel 可以使用不同顺序；
- 绑定规则按 `priority ASC` 顺序执行；
- 全局规则按创建时间升序执行，并在绑定规则之前执行；
- 同一 ProviderModel 下同一规则不得重复绑定；
- 规则被禁用、软删除或不满足匹配条件时，不执行；
- 规则管理页显示规则的全局启用状态，模型配置页显示绑定启用状态。

### 4.4 失败策略

默认采用“失败即阻断当前 attempt”：

- JSON 无效、路径类型不匹配、值校验失败或受保护 Header 被修改时，规则执行失败；
- 当前 attempt 不得向 Provider 发送不完整或未确认的请求；
- 如果尚未向客户端写出响应，返回本地明确错误；
- 不应把规则配置错误当成 Provider 故障自动切换；
- 日志记录规则 ID、规则名称、动作类型和安全的错误摘要，不记录密钥和完整正文。

后续可以增加“跳过并继续”，但不作为首期默认行为。

## 5. 首期规则能力

### 5.1 匹配条件

规则可以包含可选匹配条件；全部条件满足时执行。当前实现支持：

- 客户端协议：OpenAI Completions、OpenAI Responses、Anthropic Messages；
- 上游协议：同上。

匹配条件为空表示对绑定该规则的所有适用请求生效。普通规则通过 ProviderModel 绑定确定生效模型，全局规则对所有供应商模型生效，因此不再额外提供请求路径、逻辑模型或 ProviderModel 匹配条件。条件应在执行前校验，不能使用任意代码表达式。

阶段不属于规则匹配条件，而是动作级字段；同一条规则可以同时包含 request 和 response 动作。

### 5.2 Header 动作

当前实现提供结构化 Header 动作：

- `set`：设置 Header，已有值被替换；
- `append`：追加值；
- `remove`：删除 Header。

Header 名称按 HTTP 不区分大小写处理。明确允许修改 `User-Agent`。以下 Header 由代理托管或具有安全含义，默认禁止规则修改：

- `Authorization`、Provider 认证 Header；
- `Host`；
- `Content-Length`；
- `Connection`、`Transfer-Encoding` 等逐跳 Header。

规则执行完成后，由代理统一重新计算 `Content-Length` 和必要的传输 Header。

### 5.3 JSON Body 动作

当前实现提供受限 JSON Path 操作：

- 设置路径值；
- 删除路径值；
- 对字符串值执行精确替换；
- 值直接按 JSON 值写入；

要求：

- 仅对 JSON 请求/响应生效；
- 路径不存在时，“设置”可创建路径，“删除”和“替换”默认视为不匹配；
- 路径类型不匹配时规则失败；
- 不对路径深度、Body 大小、查找/替换串长度或单次替换数量设上限：这是本地工具，规则由用户自己编写自担；
- 正则替换按整段文本求值，文本较大或模式容易回溯时可能明显变慢，界面在开启正则时提示该性能风险；
- 不支持任意数组遍历表达式和代码执行。

当前实现的 JSONPath 语法只支持以 `$.` 开头的简单点号路径，不支持数组遍历、过滤器或复杂表达式。

### 5.4 thinking/reasoning

thinking/reasoning 不是三个协议中完全同构的字段。当前实现尚未提供协议预设，仅保留通用 JSON 动作能力；后续如需支持 reasoning/thinking，建议再补协议预设层：

- 每个预设声明目标协议和目标字段路径；
- 预设底层仍转换为普通结构化 JSON 动作；
- 不支持的协议字段必须在保存或执行前明确报错；
- 响应修改器不得静默删除、移动或伪造模型输出中的思考内容；
- 需要区分“请求中的 reasoning/thinking 配置”和“响应中的 thinking 内容块”。

当前实现没有针对 reasoning/thinking 的专用预设，也没有单独的协议字段矩阵；相关需求仍属于后续设计。

### 5.5 脚本动作

结构化 Header / Body 动作表达不了「读完内容再决定怎么改」这类逻辑（例如「只有 `messages` 里出现过某个标记，才把 `temperature` 改成 0」）。脚本动作用一小段用户代码补上这块：它读当前阶段报文，交回改写结果。

脚本以**函数体**形式书写（不写 `function` / 不写 `return` 之外的包装），可以直接 `return`：

```js
// 只有正文里出现 "apply-strict" 时，才把 temperature 压到 0；
// 没命中就不 return，这条动作整个不改动。
if (body && JSON.stringify(body).includes('apply-strict')) {
  return { body: { ...body, temperature: 0 } }
}
```

注意上面这个例子**只交回了 `body`**：交回的 `body` 整体替换当前 body，而没交回的 `headers` 保持不变。
要删一个字段，就靠「交回完整 body、但不写那个字段」来表达（下文有例子）。

脚本可见的全局（没有 `require` / `process` / 定时器 / 网络 / 文件系统）：

| 名字 | 含义 |
| --- | --- |
| `body` | 当前阶段报文的解析结果；正文不是合法 JSON 时为 `null` |
| `headers` | 当前阶段报文的 Header（只读副本） |
| `protocol` | `{ stage, clientProtocol, upstreamProtocol }`，只读 |
| `get(path)` | 按 JSONPath 取值，语义同 §5.3 |
| `console.log/warn/error(...)` | 写入规则测试结果的日志区，最多 50 行 |

交回约定：

- `return { body, headers }`：**交回谁就整体替换谁**——脚本没写的字段 / 键即视为删除（这是删掉一个字段唯一可行的表达方式），所以通常用 `{ ...body }` / `{ ...headers }` 起手；
- `return` 空值（`undefined` / `null` / 不返回），或返回的对象里两个键都没出现：整条脚本不改动报文；
- 返回其它类型（数字、字符串、数组）：规则失败；
- body 解析失败时**不**直接报错，而是把 `null` 交给脚本，由脚本决定是否 `throw`——「是不是 JSON」本身就是脚本可能要判断的事。

删字段就靠这条替换语义表达（结构化动作里的 `remove` 只能删到路径为止，脚本可以一次删干净）：

```js
// 交回完整 body，但把 metadata 这个键丢掉 —— 整体替换之下它就被删了。
const { metadata, ...rest } = body || {}
return { body: rest, headers: { ...headers } }
```

约束与失败语义：

- 脚本同样受 §4.4 的「失败即阻断当前 attempt」约束，抛异常、超时或交回非法结构都会失败；
- 与结构化动作一致地禁止修改受保护 Header（§5.2）：按**改动前后取值是否不同**判定，脚本改了受保护 Header 视为规则失败，原样带回去不算违规；
- 脚本不得改动投递形态字段（`stream`），同样按「改动前后取值不同」判定；
- 单次执行有超时上限（默认 1 秒，最大 5 秒），死循环被中断而不是挂住代理；
- 与结构化 Body 动作一样，脚本动作只对完整 JSON 报文生效，流式响应按 §6 跳过；
- 脚本是本地用户自己写的代码，隔离的目标是「防手滑、防死循环」，不是抵御恶意代码。

## 6. 交付形态边界

规则动作能不能生效，取决于**当前阶段手里拿的是不是一整份正文**，而不是取决于客户端跳的是哪条 `transport`。这两件事不是一回事：`transport` 是「用哪种方式跑」的约定，交付形态是它派生出来的一个结论。内核把它抽成一根独立的轴 `BodyDeliveryShape`（`whole` 整包 / `incremental` 向下分帧 / `duplex` 双向多轮），传输形态到交付形态的换算是**穷尽的**，没有兜底分支：

| 传输形态 `transport` | 交付形态 `BodyDeliveryShape` | 请求阶段 | 响应阶段 |
| --- | --- | --- | --- |
| `http` | `whole`（整包） | 生效 | 生效 |
| `http-stream` | `incremental`（向下分帧） | 生效 | 跳过（`skipped`） |
| `websocket` | `duplex`（双向多轮） | 未实现 | 不适用（`not-applicable`） |

三条边界，语义各不相同，不能混为一谈：

- **`http`（整包）**：请求与响应都拿得到一整份 JSON，两个阶段都照常执行；
- **`http-stream`（`incremental`）**：请求阶段照常执行（发上游前已经攒齐）；响应阶段**跳过**——响应一旦开始向下分帧，就不能撤回或切换 Provider，也不通过默认全量缓冲来规避这一点。跳过是**逐条报理由**的（`unsupported-shape`），不是默默不动；
- **`websocket`（`duplex`）**：双向多轮没有「一份响应正文」这个概念，响应阶段的改写**不适用**。这不是「今天还没做」而是「用错了」——所以试跑入口对 `websocket` 直接回 `TRANSPORT_NOT_IMPLEMENTED`（501 语义，HTTP 状态 400），与真实入口对同一个请求的答复保持一致；若引擎在响应阶段收到 `duplex`，会立刻抛错而不是静默跳过，避免出现「试跑报成功、真跑回 501」两个答案。

「跳过」（`skipped`）与「不适用」（`not-applicable`）刻意是两个值：前者是「这个形态今天不处理这条」并可继续请求，后者是「这个形态压根没有能被处理的对象」。把它们塌缩成同一个值，正是这条轴最初出问题的原因——`websocket` 被兜底成「整包」，于是同一个请求在试跑里「改造成功」，在真实入口却回 501。

### 6.1 流式响应的事件级改写（设计草案，待评审）

**这一节记录的是一处尚未闭环的能力缺口，而不是已实现的行为。** 现行响应阶段对 `incremental` 一律跳过（§12 的 C/C2 行），意味着**响应改写对占绝大多数的 SSE 请求完全无效**——把所有规则都写完，流式请求的响应字段一个也改不到。这是本功能当前最大的短板：请求阶段照常生效，响应阶段在主用例上是空转。本节把「怎么补」写清楚，作为 §12 D 行所要求的**独立设计评审**的输入；评审通过前不写实现代码。

#### 为什么不能复用整包动作

所有既有动作都经由 `applyBody`：把整份正文 `JSON.parse` 成**一份文档**，再按路径 `get`/`set`。SSE 流里没有这样一份文档——它是一串 `data: {...}\n\n` 事件，每个事件是**局部增量**（`choices[0].delta.content`），没有根节点可供寻址。因此不是「把开关打开」就能用，缺的是动作语义。

但**底座已经够用**，这也是本能力可行的前提：

- `frame-pipe.ts` 的 `applyFrame` 拿到的是**原始 `data` 帧字节**，且允许返回 `null`（丢弃）、数组（拆帧）或新帧——逐帧改写是一等公民；
- `protocols/shared/response-conversion.ts` 已有 `parseSseIncremental(buffer)`，能把被 TCP 分帧**切断**的事件重新拼成完整事件，并交回未消费的余量。

顺带澄清一个常见误解：**协议转换本来就在逐事件工作**（`protocol-conversion` 修改器没有形态限制，靠 `parseSseIncremental` + `createSseConverter` 在流内逐事件转换）。被形态跳过的是**用户改写规则**，不是「流不能被逐帧处理」。

#### 执行模型：缓冲到「事件边界」，绝不攒整份

新增一条响应改写分支（`scope: { shapes: ['incremental'] }`），在**协议转换之后**运行（这样它面对的事件已经统一成客户端协议，与整包分支的次序一致）：

```
data 帧 → carry += chunk
        → [events, carry] = parseSseIncremental(carry)   // 复用现有解析器
        → 对每个完整事件：
             data === '[DONE]'         → 原样透传（哨兵）
             JSON.parse 失败 / 非对象   → 原样透传（无路径可寻址）
             否则得到「事件对象」        → 按规则改写 → serializeSseEvent 重新成帧
end 帧 → flush 残余 carry（通常为空；非空则原样透传，不臆造事件）
```

硬约束（评审须逐条确认）：

1. **延迟上界是单个事件，不是整条响应。** 只允许缓冲到「下一个事件边界」，禁止攒整份正文——否则流式的首字延迟优势直接消失，等于把流退化成非流式。
2. **超时按单事件计**，不按整条响应计；沿用 §5.5 的 `node:vm` 沙箱与超时上限。
3. **非 JSON 与 `[DONE]` 必须原样透传**，绝不吞帧（吞掉 `[DONE]` 会让客户端永远等不到结束）。
4. **观测与计费不受影响。** `frame-pipe.ts` 里 `notifyObservers` 在修改器**之前**看的是上游原始字节（`usage.ts` 从末尾事件累计 token），改写发生在之后，天然不污染统计；评审需把这个前提固化为断言。

#### 动作模型到事件的映射

| 动作 | 在事件级上的含义 |
| --- | --- |
| `body-*`（`body-replace` / `body-set` / `body-remove` …） | `path` 作用于**事件对象**，如 `choices[0].delta.content`、`delta.reasoning_content` |
| `script` | `body` 是事件对象，返回契约不变：`return { body }` 省略即删、不 `return` 即不动、抛错即失败 |
| `header-*` | **对流式响应天然不适用**：HTTP 头在第一帧就已发出，中途改不了。必须在 UI 显式标注或直接拒绝，不能静默无效 |

#### 事件目标选择（否则常见需求无法表达）

一串事件里「改哪一个」必须可指定，否则「替换首块的 `model` 名」「只清理携带 `reasoning_content` 的 delta」这类需求无解。候选谓词（评审需定集合）：

- 事件类型：SSE `event:` 名，或载荷内 `type`（如 Anthropic 的 `content_block_delta`）；
- 路径存在性：仅当 `delta.content` 存在时命中；
- 序号：首帧 / 末帧；
- 载荷字段匹配：如仅当事件内 `model === X`。

#### 三协议的事件 schema 差异（评审核心）

三种协议的流式事件结构完全不同，这是本能力最需要拍板的地方：`openai-completions` 是 `choices[].delta.{content, reasoning_content, tool_calls}`；`anthropic-messages` 是 `type: message_start / content_block_delta / message_delta / message_stop`；`openai-responses` 是一串 `type: response.*.delta`。两条路线：

- **协议相关 path**：动作直接对上游/客户端协议的事件结构寻址，直观但与协议强耦合；
- **归一化事件视图**：先投影出一个跨协议统一的事件形状再改写，复用转换层已有的归一化经验，但需要在改回时无损还原。

此外，首末帧常携带特殊载荷（OpenAI 首块带 `role`、Anthropic `message_start` 带 `usage`），改写或删除它们可能破坏客户端解析，需要决定是否保护。

#### 试跑与管理 API

`/api/request-rewrite-rule/test` 当前入参是「一整份 body」。事件级需要把入参扩展成「一段事件序列」（JSON 事件数组，或原始 SSE 文本），`TestSchema` 与试跑面板一并调整；否则试跑只能验非流式，照旧给出「流式无动作」的假象。

#### 待评审拍板的开放问题

1. 走协议相关 path，还是归一化事件视图？
2. 事件目标选择支持哪些谓词（上节四项取哪几项）？
3. 首末帧特殊载荷是否需要保护（`role` / `usage`）？
4. 首期是否只支持一种协议（建议 `openai-completions` 先行，另两种按需跟进）？
5. 试跑入参形态如何表达「一段事件序列」？
6. 事件级改写的失败语义是否与整包一致（当前尝试失败）？

### 6.2 响应阶段已被功能闸门关闭（当前状态）

鉴于 §6.1 的能力缺口，**响应阶段改写当前整段关闭**——入口关掉，代码与类型保留。

理由与 §6.1 的开头呼应：非流式响应能改，但占绝大多数的 SSE 流式请求改不了，而用户在「响应」阶段配好一串动作、到真实请求才发现流式下**什么都不发生**。静默地不做，比不提供这个阶段更糟：前者让用户以为规则生效了。因此在这个缺口补齐（§6.1 评审通过并落地）之前，产品层面不开放响应阶段。这与 §6 的「能力判定」是两根正交的轴：§6 回答「这份正文在这种形态下能不能按路径改」，闸门回答「这个入口今天开不开放」。

关闭的是**入口**，不是**能力**：

| 关闭的入口 | 位置 |
| --- | --- |
| 动作编辑器的阶段下拉不再列出「响应」 | `action-editor.tsx`（遍历 `@common/features` 的 `ENABLED_RULE_STAGES`） |
| 测试用例的阶段下拉不再列出「响应」 | `rule-editor-dialog.tsx` |
| 内核不再注册 `response-rewrite` 修改器，响应规则一次都不执行 | `createResponseModifiers`（`RESPONSE_REWRITE_ENABLED` 为假时跳过注册） |
| 写入（`create` / `update`）与试跑（`test`）拒绝带响应阶段的请求 | 管理 API 回具名错误码 `RESPONSE_REWRITE_DISABLED`（HTTP 400） |

界面藏起选项只是第一道：脚本、旧数据或第三方客户端仍可能把带响应阶段的请求打进来，只靠界面藏等于把闸门交给调用方自觉，因此管理 API 也挡一道。

**没有关闭的**（避免把「关闭」做成「删除」）：

- `RuleStage` 类型、`RequestRewriteRuleActionSchema.stage`、`delivery-shape.ts` 的 `stageShapeSupport` / `isStageRunnable` 及其单测——它们是**能力**的表述，原样保留，`delivery-shape.test.ts` 继续断言 `stageShapeSupport('response', 'incremental') === 'skipped'`、`('response', 'duplex') === 'not-applicable'`；
- 响应改写修改器与引擎实现（`createResponseRewriteModifier` 单独导出、`applyRequestRewriteRules` 的响应阶段语义完整），并有直接覆盖它们的单测；
- 库里既有的响应阶段数据（如果存在）仍能读出。

重新开放只改一处：把 `packages/contracts/source/features.ts` 的 `RESPONSE_REWRITE_ENABLED` 翻回 `true`。它是被标注成 `boolean` 的常量（而不是字面量 `false`），因此 `if (RESPONSE_REWRITE_ENABLED)` 的两条分支都会留在打包产物里，不会被死代码消除裁掉——那才是真正意义上的删除。

## 7. 数据模型

两张表的字段、主键与索引定义在 [data-model.md](./data-model.md) §3.13，这里只写字段之外必须知道的约定。

- `match`、`actions` 和 `testCases` 是真正适合 JSON 的内容，由 Zod 校验；名称、启用状态、阶段、时间等查询字段一律不放入 JSON。`scope` 取 `global` 或 `model`，决定是否自动应用以及模型窗口是否可编辑。`source` 取 `user`、`builtin` 或 `imported`。
- 绑定表主键为 `(providerModelId, requestRewriteRuleId)`：一条绑定要么在，要么不在；**取消绑定再加回来是在同一行上复活**（主键冲突更新并把 `deletedTime` 清回 `null`），不会新增、也不撞历史行。同一 ProviderModel 下同一个 `priority` 只能有一条生效绑定，这条由应用层把关（不做成部分唯一索引：违反它的是用户在一个请求体里填了两个相同的优先级，那是输入问题，该收到一句能照做的 409，而不是从 SQLite 消息里抠出来的列名）。绑定表不保存规则副本——请求执行时读取规则快照，历史 attempt 只记录规则 ID 列表。
- 首期不新增端点级绑定表。若后续确认同一 ProviderModel 的不同协议必须有不同规则链，再扩展为 `provider_model_endpoint_request_rewrite_rules`，并同时定义模型级默认规则与端点级覆盖关系，不能直接叠加两套隐式规则。

### 7.1 观测数据

当前实现不新增完整规则执行正文表。请求详情 UI 按阶段展示已有的采集内容。规则按 ProviderModel 匹配，归属单位是「尝试」，因此命中的规则 ID 写入 `request_attempts.requestRewriteRuleIds`（请求阶段）和 `request_attempts.responseRewriteRuleIds`（响应阶段），客户端视角的 `request_contents` 不保存规则 ID。

规则命中是**事实**而不是载荷：`captureRequestContent` 关闭时它依然完整落库。正因为如此，它不能寄居在 `attempt_contents` 上——正文表会随采集开关整体消失，把事实和载荷放在同一张表里等于让开关决定事实是否可查。协议转换同理，由 `request_logs.clientProtocol` 与 `request_attempts.upstreamProtocol` 对比得出，不单独建表。暂未记录：

- 规则链版本或快照摘要；
- 跳过、失败的规则明细；
- 规则错误码；
- 修改前后字段数量等非敏感统计。

不得保存 Authorization、API Key、完整原始 Body 或未脱敏 Header。

## 9. 控制台设计

### 9.1 独立“请求修改”菜单

当前前端已经有一级菜单“请求修改”，页面采用主从工作区：

- 左侧：规则列表、搜索、启用筛选、使用模型数量；
- 右侧：规则详情与编辑器；
- 支持新建、编辑、复制、启用/禁用、测试和删除；
- 删除前显示使用中的 ProviderModel 数量，并要求确认；
- 规则保存前执行前端基础校验，最终以服务端校验为准。

### 9.2 规则编辑器

编辑器按以下区域组织：

1. 基本信息：名称、描述、启用状态和全局应用；
2. 匹配条件：客户端协议和上游协议；
3. 动作列表：每个动作显示类型、路径/名称和值；
4. 测试阶段：请求或响应的测试用例，以及该用例的传输形态；
5. 保存和取消。

当前实现使用结构化控件编辑动作，并通过规则测试接口验证修改结果。脚本动作（§5.5）用同一套控件，但值区域换成一个带基础类型提示的代码编辑器（光标在 `get('` 或 `body.` 后给出字段路径候选、在裸标识符处给出 `body` / `headers` / `protocol` / `get(...)` / `console.log(...)` 候选），并用一个输入框配置超时上限。测试结果区在命中脚本动作时额外展示脚本日志。

测试用例带**传输形态**选择器（§6）：试跑要能复现「这条规则在这种形态下到底会不会生效」。当所选形态下当前阶段不可跑时，测试区顶部给出警告——响应阶段 + `http-stream` 提示「流式响应不会执行响应阶段改写」，`websocket` 提示「WebSocket 未实现」——而不是让用户对着一份「改造成功」的结果以为它在流式下也生效。结果区同时列出**每条被跳过规则的原因**（禁用 / 已删除 / 无当前阶段动作 / 协议不匹配 / 形态不支持），让「为什么没生效」当场可答。

脚本动作的两处辅助设计，都是为了压低「第一次写脚本」的门槛：

- **切到脚本即填入起始脚本**。空白编辑器对没用过的人无从下手，而一段能直接跑通的基线代码本身就是最好的说明。起始脚本按阶段区分（请求阶段读请求、响应阶段读上游响应），用户改两笔就能用。**切换报文阶段时起始脚本跟着换**（`shouldReseedScript`）——请求基线与响应基线读的是两份不一样的报文，把请求脚本留在响应阶段等于给用户一个跑不通的起点；但只在编辑器里仍是「原阶段的默认基线」（用户没动过）时才替换，改过几笔就保留不动。
- **动作行内提供「插入示例」下拉**（`rewrite-script-samples.ts`），把整段起始脚本换进编辑器。示例**少而准，按阶段成对**：请求侧是基线 / 删字段 / 条件改写，响应侧是基线 / 清理推理字段 / 条件改写。下拉**按当前动作阶段过滤**（`rewriteScriptSamplesForStage`），请求脚本只列请求示例，不会把一段只在响应阶段才跑的代码插进请求脚本。示例刻意覆盖三类结构化动作表达不出来的意图：删字段（整体替换语义下省略即删除）、按内容过滤（不 `return` 即不动）、以及响应侧的清理。示例代码里的注释保持英文：这些字符串会原样进代码编辑器，跟着界面语言翻译反而破坏可读性；示例的**名称与说明**才走 i18n 目录。

### 9.4 内置规则模板

「新建规则」是一个下拉：第一项是空白规则，后面是内置模板。选模板会得到一条**动作已经填好**的草稿，
而不是让用户对着空动作列表猜该填什么。

| 模板 | 动作 | 用途 |
| --- | --- | --- |
| 修改 User-Agent | 请求 Header `set` `User-Agent` | 隐藏真实客户端标识；默认值 `OSW/<应用版本号>` |
| 移除请求头 | 请求 Header `remove` `cookie` | 摘掉本地会话 Cookie |
| 设置请求字段 | 请求 Body `set` `$.temperature` | 固定采样参数 |
| 按脚本条件改写 | 请求脚本动作 | 先读正文再决定改不改；演示结构化动作拼不出来的「看内容再决定」 |

约定：

- 模板只填草稿，**不落库、不生效**；用户保存后与手写规则完全等价（`source: 'user'`），
  不会变成一种「不可编辑的内置规则」。草稿靠 `updatedTime === null` 标记。
- 模板的名称与说明取自创建时的界面语言，并作为规则名/描述写进草稿，用户可以自由改写。
- 模板不设置 `scope: 'global'`，是否全局由用户决定。
- 模板自带一条可直接运行的测试用例，套用后能立刻看到动作效果。
- 模板刻意只有四个，覆盖「改一个头、删一个头、改一个字段、写一段脚本」这四种最常被问到的形态。
  删除字段、文本替换、响应阶段等动作编辑器本来就支持，用户照着搭即可；
  模板一多，下拉就变成要先通读一遍才能选的目录，反而拖慢「新建一条规则」这个动作。
- 「按脚本条件改写」是唯一的脚本模板，它唯一能教的事就是脚本的**必要性**：
  「只有正文里出现过某个标记才动手」用结构化动作拼不出来，而它自己的用例也能直接跑通。
- 示例字段选三种协议根级都存在的 `temperature`，示例 Header 用通用的 `user-agent` / `cookie`，
  因此模板都不写匹配条件：只想覆盖一个 Header 的规则，不必先想清楚协议矩阵。
- 「修改 User-Agent」的默认值是 `OSW/<应用版本号>`，版本号取构建时的 `package.json`
  （Vite `define` 注入的 `__APP_VERSION__`），所以默认值声称的就是当前这个二进制，
  而不是某个随版本迭代变成假话的写死字符串。
- 模板定义留在渲染层（`packages/console/source/pages/.../rule-presets.ts`），不放进 `@common`：它没有服务端用途，
  与智能路由预设（服务端要在没有存过图时直接执行，因此必须在 `@common`）的约束不同。

## 10. 供应商包导入导出

供应商包（`/api/provider/export`、`/api/provider/import`）不包含请求重写规则：

- 不导出规则稳定 ID、名称、阶段、匹配条件和动作；
- 不导出 `provider_model_request_rewrite_rules` 绑定及顺序；
- 导入不会写入、删除或改写规则本体，也不会重建绑定顺序；
- 包内可选的 `apiKey` 是唯一可能出现的凭据，且必须由用户显式勾选；包不包含任何完整请求或响应正文。

规则本体是与供应商并列的独立实体，把绑定导出到另一个环境只会得到指向不存在规则的悬空引用（外键也不允许），因此规则需要单独迁移。

需要注意的副作用：包里没有的模型会在导入时软删除，其规则绑定随之失效；模型再次导入时得到的是新 ID，旧绑定不会自动恢复。

## 11. 安全与隐私

规则能力位于本地管理服务和代理核心之间，仍必须遵循现有安全边界：

- 管理服务不校验身份，边界只有回环监听与来源白名单（它固定监听回环，见 [security-privacy.md](./security-privacy.md) 的「访问控制」）；
- 不允许规则访问网络、文件系统、环境变量或密钥环（脚本动作在 `node:vm` 沙箱内执行，关闭 `eval` / `new Function` / WASM 编译，不提供 `require` / `process` / 定时器）；
- 不允许规则覆盖 Provider 认证信息；
- Header 和 Body 修改结果遵循现有脱敏策略；
- 规则错误消息不得包含 Authorization、API Key 或完整 Body；
- 仅对单条规则的动作数量保留结构上限；不对 Body 大小、路径深度或替换次数设上限，本地工具不做资源消耗攻击假设；
- 正则替换的长文本性能风险由界面提示，用户自行判断；
- 规则变更应记录操作日志或至少记录更新时间，便于定位请求行为变化。
