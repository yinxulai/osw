# 桌面端产品形态

## 技术栈

Electron + Node + TypeScript + React/Vite，选型理由与版本要求见 [tech-architecture.md](./tech-architecture.md)。

## 主要入口

### 菜单栏 / 托盘

- **macOS**：菜单栏图标
- **Windows**：系统托盘图标
- **Linux**：系统托盘（P1 完善）

### 菜单快捷区

托盘菜单结构固定为三组，不随状态增删条目：

1. **代理服务**
   - 状态行：`运行中 · <端口>` / `已停止`（不可点击，它说明下面那组操作的对象是什么）
   - 复制接入地址：子菜单按客户端类型列出两个 Base URL（`OpenAI · <origin>/v1`、`Anthropic · <origin>`），点一条复制一条
   - 启动 / 停止代理服务：一个条目按当前状态切换文案，文案本身就是动作
2. **打开主界面**
3. **退出 OSW**

macOS 会额外渲染一个原生分组标题「代理服务」（Electron 的 `type: 'header'`，macOS 14+ 才支持）；
其他平台没有标题语义，只用分隔线分组。

菜单栏 / 托盘只提供上述基础操作，逻辑模型、供应商和监听配置统一在主界面管理。

在 macOS 上关闭主窗口不会退出应用：代理和菜单栏图标继续运行，同时隐藏 Dock 图标；从菜单栏重新打开主界面时恢复 Dock 图标。

### 状态面板

左键点图标弹出一块面板（macOS / Windows；Linux 的 StatusNotifierItem 对自定义弹层支持不稳定，保留右键原生菜单）；右键仍是上面那份原生菜单，键盘与无障碍用户始终有一条不依赖自绘 UI 的路径。

面板内容：代理启停与地址 → 逻辑模型的页签 → 每个逻辑模型当前的候选供应商模型（协议、TPS / TTFT、徽标），徽标用与控制台同一套推导，**处理中（n）** 的 n 是实时在飞的请求数。
面板高度由内容决定，宿主只负责把它摆在图标旁边、贴边收口，并在失焦 / Esc 时收起。

**面板不是主进程拼出来的静态页**：它是控制台那份产物里的第二个 HTML 入口（`packages/console/tray.html`，构建落在 `render/tray.html`），与主界面共用同一套组件、查询、实时流与推导，只是不挂路由与侧边栏。
宿主那边（`apps/app/source/tray-panel.ts`）只剩窗口那点事：位置、高度、开合。所以面板里显示的状态**不可能**与控制台不同步——它们本来就是同一份数据算出来的。

面板不写 `localStorage` 之外的任何偏好，也不向主进程回写主题：它是同一份产物的另一个窗口，主题与语言读的就是控制台那套偏好。

### 图标状态

**图标不表达状态**：所有平台、所有运行状态共用同一张单色图标（macOS 走 template image，由系统按菜单栏明暗自动着色；
Windows / Linux 为白色），状态由菜单第一行与鼠标悬停提示表达。

不用颜色当状态通道的原因：macOS 的 template image 由系统接管着色，应用提供的彩色不会被采用；
Windows / Linux 的托盘底色随系统主题变化，彩色图标在浅色底上会糊成一团。
而菜单第一行能直接写出端口号，比一个色点准确。

### 逻辑模型页

管理每个逻辑模型的自动切换候选列表，每个列表项是一个 ProviderModel：

- 逻辑模型卡片（模型名 `modelId`、说明、内建默认标识）与新增 / 改模型名 / 改说明 / 软删除逻辑模型；改模型名与删除落在卡片头右侧、与第一行同高的一排幽灵按钮上，按钮与模型名同行，hover 或键盘聚焦才浮现。这排按钮**不铺自己的底色**：它出现时右侧的切换器会同时让出同样宽的位置，按钮下面是空出来的卡片底，再盖一层渐变或模糊只会显出半透明的一块脏色（模型行上的遮罩则相反——它压在供应商链接、指标与状态徽标之上，非模糊不可）。**改模型名会顺带改写引用它的路由定义**（图的落点与固定条件、规则表的落点与固定条件），否则一次改名就会让引用它的定义指向一个不存在的落点；卡片上的模型名就是客户端请求要发的模型名，数据记录 id 是本机内部主键，不出现在界面上
- 模型列表（协议类型、远端 URL、Provider API 模型名、Provider、优先级、启用状态、ProviderModel 健康状态）
- **当前使用标识**：高亮显示当前正在使用的列表项
- 新增 / 编辑 / 删除列表项；「添加模型」是候选列表末尾多出来的一行（同宽、同左内边距、hover 才浮出底色，比模型行矮一档），不是卡片头上的按钮——它是候选列表的下一行，而不是这张卡的头等操作。这一列的行本身没有边框、只用发丝线分格，所以它也不做虚线框：那样会在这里多出第三种形状（尺寸取自路由规则「再加一条」，但那处的条件行本来就是盒子，虚线才成网格）
- 卡片内容是**整块通栏**的：列表、空状态、末尾的「添加模型」都贴到左右边缘，只在卡片头保留内边距。因此卡片底部不留内边距——这一行直接与卡片下边缘齐平，否则列表走完后会在末尾多出一条既没有发丝线收尾、也不属于任何一行的空白带
- 拖拽调整候选顺序（优先级）
- 顶部指标卡汇总该逻辑模型的关键指标（请求成功率、平均响应耗时、平均 TPS、当前可用模型）。每张卡只有「标签 + 数值」两行：口径说明压在标签右侧的 info 图标上，悬停或聚焦才展开，不铺成第三行小字——四张卡里只有算得复杂的指标写得出口径，摆在一起就是两行与三行参差，还把「看一个数」变成「读一句话」。缺数据时数值位照旧占位（用 `—`），不因为没数据就换一种版式

> 内建默认逻辑模型 `default` 是未命中任何逻辑模型时的落点，因此它的名称不可改、也不提供删除入口（说明仍可编辑）；其余逻辑模型可自由创建、改名与软删除。软删除只打 `deletedTime` 时间戳，历史请求日志、调度绑定与路由图落点仍按 ID 引用得到它。详见 [data-model.md](./data-model.md)。

### 模型管理页

- Provider 列表（名称、状态、连续失败、冷却状态）
- 新增 / 编辑 / 删除 / 启用禁用 Provider，并管理其下的 ProviderModel 与端点绑定
- 配置空闲超时时间（两次数据间隔，流式不超时）
- 连通性测试：复用真实模型请求链路验证密钥与端点
- 导入 / 导出供应商包：单个供应商详情可导出，列表页可导入或导出全部；导入前展示包内供应商、将被覆盖的同名供应商数量和明文 API Key 条数，详见 [provider-model.md](./provider-model.md)

### 请求记录页

- 最近请求列表（状态、时间、逻辑模型、协议、传输形态、输入 / 缓存 / 输出 Token、TTFT、TPS；列口径见 [observability.md](./observability.md)）
- 查看某次请求的详细尝试过程（每个候选 ProviderModel 的结果）
- 查看完整客户端请求/响应和每次 Provider 尝试内容
- 有协议转换时查看转换前后的请求/响应内容
- 使用抽屉或对话框打开详情，支持格式化、复制和折叠
- 筛选：按模型、协议、供应商、状态、时间范围
- 日志字段、采集开关与保留策略见 [observability.md](./observability.md) 与 [data-model.md](./data-model.md)

### 客户端配置页

这一页只回答两件事：**哪些客户端还没指向 One Switch**，以及**哪些已经留了可回退的版本**。所以主版面是一张客户端列表——一行一个，左边是客户端自己的图标与名字，右边是配置覆盖状态、最近更新时间与版本数，页头右上角一颗「全部生成配置并应用」把能自动改的一次性改完；点任意一行进详情，看那份配置文件的原文与历史版本。

不把表单直接铺在主页，是因为客户端名录会一直变长：摊开后「另一多半」永远只是列表里的一行说明。列表先给全局，再逐行下钻，两边都不挤。

列表上面是**并排两张**参考卡，回答同一个问题——「我手上的工具不在下面这份名单里，怎么办」：左边「接口地址」（能照抄，地址收进凹槽、行尾一个复制入口），右边「支持哪些接口」（哪些路径算接上了，铺开摆）。左值右接口是最短的查找路径；两张卡与引导第二步用的是**同一对组件**（`components/address-card.tsx` 传 `layout="cards"`、`components/interface-table-card.tsx`），不在这里维护第二份路径清单。两张卡底边对齐（网格 `items-stretch`）——内容一多一少时底边参差会显得整块版面缺了一角，而它们本就是一组的左右两半。

详情页的版面是单调的一列：文件选择（一个客户端可能声明多个文件）→ 「要写入的模型」→ 文件正文。**写入只有一处**：页头右上角并排的「撤销改动」「保存内容」——保存一次写回所有改动过的文件，撤销只退当前展开的那一份；内容模块里只留一颗只改内存草稿的「生成配置」（按本机服务把推荐内容填进编辑区，落盘仍要靠保存）。版本历史不属于任何一列内容——手动保存与自动填充都会产出版本，它管的是整页，所以是页头最右那枚图标按钮（在保存/撤销右边），点开才占地方。这里不再有单独的一颗「一键生效」：那会把「哪一下才算数」变成一道选择题，列表页的「全部生成配置并应用」仍在（那里没有编辑器）。

- **只让用户决定模型**：选哪个模型是用户自己的取舍（本机服务不校验它，任何非空名字都受理）。模型从**逻辑模型**清单里选（写进配置文件的必须是逻辑模型的 `modelId`，引擎就是拿请求里的模型名去找落点的），右边一枚铅笔可以切成手动输入：先写个名字、回头再建逻辑模型也是常事；文件里的值不在清单里时（别人手改过、或那个模型已被删）一进来就是手动模式，否则下拉找不到匹配项只会退回占位符，看起来像「什么都没选」。小模型留空即回落到模型。**出现几行由登记表（`packages/contracts/source/clients/<key>/definition.json` 里每个客户端的 `apply` 配方）推出来**：Claude Code 那一批写同一个值的模型键（别名、主模型、子代理模型，以及各别名在 `/model` 选择器里的展示名 `*_MODEL_NAME`）合成一行，只认主模型的客户端就只有一行
- **地址不让改、也看不到输入框**：客户端要指向的就是本机服务本身，这条地址只有一种正确答案，所以既不展示输入框也不让人改，由服务端按当前监听设置就地写入（配置里同时写入固定样例密钥 `sk-osw`，见 `packages/contracts/source/client-config.ts`——本地不校验鉴权，它只是给客户端一个非空的占位）。需要看这条地址的人去引导第二步（那里还有就地改客户端配置的编辑器），或者就看上面这张参考卡
- **保存按钮报出「改了几处」**：只有一份改动时它写「保存内容」，多于一份写「保存全部（N 份）」，没有改动就置灰；旁边的「撤销」只退当前展开的那一份。改动明细不铺成单独一块版面——文件正文与版本历史已经能把「改了什么」说清，再来一行摘要只是把同一句话说第二遍
- **「生成配置」只改草稿、不落盘**：它按当前选择的模型（没有就沿用文件里探测到的，再没有就落回内置默认）把推荐内容填进编辑区，用户看过、确认后再按保存写回。地址与固定样例密钥由服务端就地写入，用户不必也不该手填
- **每次写入都留一份版本**：写前把原内容存成一条版本（同内容不重复存），文件正文也可以手改保存并附一句说明，历史里任意一条都能回退
- **provider 名按环境而变**：客户端配置文件是**全机只有一份**的（`~/.codex/config.toml`、`~/.pi/agent/*.json`…），而开发实例与正式实例要跑在同一台机器上。所以写进去的 provider 名取决于**当前是哪套环境**：正式写 `osw` / `OSW`，开发写 `osw-dev` / `OSW Development`（身份表在 `packages/contracts/source/clients.ts` 的 `resolveLocalProviderIdentity`，开发环境会随执行 `ServerRuntime.start()` 就地配置）。同名就意味着开发实例写的是正式那一条表项——点一下「生成配置」就把用户正在用的正式配置改到 19300 端口去了。同一份里能并排放下两条 provider 表项的客户端（Codex、OpenCode、VS Code、Pi、DeepSeek Harness）开发环境写的是**另一条**表项，与正式那条共存；装不下第二套的（Claude Code 的 `ANTHROPIC_*`、Copilot CLI 的 `COPILOT_PROVIDER_*`）则**直接忽略**——这些文件里没有任何地方能挂两套身份，写进去就是抢正式环境的位置。被忽略的客户端在列表里报 `unsupported-environment`，详情页也不摆生成/保存按钮
- 读写全部发生在管理服务（core）：只有它拿得到真实主目录与进程环境变量，也只有它手里有「注册表声明过的路径」这份白名单。控制台只说「客户端 X 的 Y 文件」，路径从不由界面拼出来——管理 API 没有身份校验（见 [security-privacy.md](./security-privacy.md)），能写哪个文件绝不能由调用方决定
- 列表行写出的是具体工具的名字与图标，所以跟着官方叫法走（注册表在 `packages/contracts/source/clients/`），改名只改一处

### 引导第一步（请求发到哪里）

数据模型决定了模型必须挂在供应商下（`ProviderModel.providerId`），所以这一步实际是**供应商 + 模型一起配**：先建个供应商（命中预设就带着地址进对话框）、填 Key，再从该供应商拉取模型并勾选。

复用正式链路（`useModelManagement` + 两个对话框组件），不重写一套「引导版」表单：拉取失败、重复模型、协议端点、转换开关这些分支在模型管理页已经被打磨过，引导页要的只是同一套交互的一个入口，另写一份等于把那些分支再赌一次。

版面是一张**供应商表**，不是「添加供应商」「添加模型」两颗并列的顶层按钮。后者把「先建谁、再给谁加模型」这层归属藏进了两段独立流程：点「添加模型」时用户根本不知道会加到哪一家（旧实现只能加到侧栏选中的那一个，而在引导页里这个「选中」是隐式的）。改成每行一个供应商（图标 + 名字 + 已接模型数）、**行尾就地一颗「添加模型」**，归属由位置表达：模型加给哪一家，就点哪一行；模型对话框里也随行带上一个可切换的**供应商下拉**，归属既看得见、也能当场改。添加新供应商则在表格下方铺开一张**宫格卡片墙**——它是这张表多出来的入口，而不是和「添加模型」平级的第二种起点（两个并列的顶层动作正是「令人迷惑」的来源）。

一个供应商都还没有时，页面直接摊开这张**宫格卡片墙**（`steps/add-model-step.tsx`）；已接入供应商时，它在表格下方以同一个 `ProviderCardGrid`（前置「添加供应商」小标题）出现——两种状态共用同一张宫格，风格、尺寸一致。首张是「自定义供应商」，其后是各内置预设，每张卡都等大、就是「新建一个这样的供应商」一个动作。命中预设就带着地址进对话框、选「自定义」就从零填——省掉「先点开下拉再挑」两层，把「这一步能做几件事」当场摆明，也让「自己有家的供应商」这条真正常见的路径站在第一位，而不是缩在菜单底部。卡片之间的点击面都是普通 `<button>`，不用 Radix 触发器，也就没有 `asChild` 包 `Button` 在 React 18 上 ref 落不到 DOM 的坑。

选路**不单独成步**：内建默认已经在下、且这套默认对新用户足够用，所以引导把它故意跳过，新手在接手之前做的每一个决定都该是为了「先跑起来」。它的产物（模型池、落点）在「路由」页随时能改，模式选择弹窗与规则表/工作流图都在那里，想调的人不必在引导里先做一遍。引导因此是一条**两步直线**：拿什么跑 → 填到哪里。

#### 不做步进器

引导**不摆步进器**（没有圆点序号、没有「第 N 步 / 共 2 步」、没有每步的标题加说明）。能省掉是因为这两步是一条直线，而「现在在哪、将去哪、能不能回头」这四件事各有更短的落点：这一屏的标题**就是这一步的名字**（`onboarding.step.*.label`，页头一个图标加一个词）；「将去哪」直接写进主按钮——**下一步：接入工具**（`onboarding.action.next` 带 `{step}`）；回头路由底部操作条上的「上一步」承担，它只在有可能回头时才有意义，因此第二步之后没有「下一步」，只有「完成」。

于是步骤名只有**一处措辞**：同一个 key 既是这一屏的标题，也是上一屏按钮上的去向，不存在两处各写一遍「这一步叫什么」而慢慢走样的机会。页面因此只有三层——页头（两句话的产品定位）→ 这一屏的标题 → 这一步的内容，中间不再夹一层与内容无关的骨架。

### 引导第二步（接入工具）

引导第二步是本机服务的**说明书**，不是任何客户端的教程：它只写三个属于我们自己的事实——服务在哪条地址上、客户端要用的值是什么、服务接受哪些路径。页面上**不出现任何工具的名字**，措辞也不借第三方的：产品名、菜单路径、字段叫法都由别人定义、随时会变，追着它们更新等于把这一页的维护成本建在别人的排期上。反过来，任何客户端都能拿这几个事实对上号，用户从客户端连不上回来时，也只需要在这几个事实里找答案。

这几个事实的单源是**组件**而不是某个页面：地址卡与接口表都归 `components/` 所有，谁要展示就 import 谁。客户端配置页顶部用同一对组件，只是地址卡各取另一档——地址卡传 `layout="cards"`（地址收进凹槽、行尾一个复制入口）。留住的是「推导只有一处」：要填什么、受理哪些路径，只能按当前监听设置与 `PROXY_INTERFACE_ENTRIES` 算出来，谁也不算第二遍。

地址卡**只给一条地址 + 一句说明**：地址（永远这一条，带不带 `/v1` 两种写法服务端都受理，这件事由说明讲清）与它会写错的那一处口径。密钥与模型名都从这张卡上拿掉——两者都不是「唯一的正确答案」（前者本地不校验鉴权、填什么都行，后者只是路由的输入、`default` 只是兜底那一个），摆出来只会让「这里真有两个值要抄」盖过地址本身；想就地改客户端配置的人，看向紧跟在下面的配置编辑器。

地址卡下面再就地嵌一块**配置编辑器**（`pages/client-config/components/client-config-editor.tsx`），把「该怎么填」从一句话变成可做的事：先是一列带品牌图标的宫格卡片墙、选一个在用的工具，下面就是它的内容卡——卡头右边一排「生成配置 / 撤销改动 / 保存内容」，点生成把它改写一遍、看过结果再按保存写回，撤销退掉当前展开的那一份，不必先跳到客户端配置页。

这一步**不摆「要写入的模型」那张卡**：引导里用户要的是「让它能用」，模型一律按内置默认逻辑模型生成，想换的人等跑起来再去客户端配置页按需改。也正因为没有模型卡，内容里那颗生成不再单摆，而是与撤销 / 保存合成一排收到**「配置内容」那张卡的卡头右边**（`ConfigEditorBody` 的 `contentActions`）——三件写入动作摆在同一处，不至于让人迟疑该从哪里下手。

配置编辑器与客户端配置页共用同一套状态（`pages/client-config/hooks/use-client-config-editor.ts`）与同一块正文（`pages/client-config/components/config-editor-body.tsx`），差别有两处：一是这里多了一层「选哪个客户端」——详情页的身份来自路由参数（「我要看这一个」），引导页没有那个前提，得让用户自己挑；二是这里省掉模型卡、写入动作整排交给调用方（`contentActions`）、生成固定走内置默认（`generateConfig(false)`）。引导里改完，正式页面里就是生效的结果，不会落到「还需要再做一遍」。

版面是**单调的一列**，顺序就是读的顺序——地址卡 → 配置编辑器 → 接口表。引导是一步一步往下读的，不摆左右布局：与客户端配置页共用的是**内容与组件**（同样的地址、同样的编辑器、同样的接口清单），不是版面；新手在这一步只需要照着往下走。

1. **地址卡**（`components/address-card.tsx`）：这一步唯一的目的地，因为几个值里只有它会写错——它有两种写法（带不带 `/v1`），两种服务端都受理。所以页面上只出现**一条**地址，另一种写法降级成一句话说明：两条并列的地址只差一个 `/v1`，抄错行是这里最贵的错误。它是全页字号最大的东西。卡上只有这一条地址与那句说明，不再摆 API Key 与模型名——它们不是「唯一的正确答案」，摆成可复制的值反而会让人以为「这里真有两个值要抄」
   - API Key 与模型名为什么不摆：前者本地不校验鉴权（OSW 不向下签发调用方凭证，见 [security-privacy.md](./security-privacy.md) 的「访问控制」），转发时会被换成渠道自己的密钥，填什么都行；后者**不是固定值**而是路由的输入——任意非空模型名都受理，命中哪个逻辑模型、最终连到哪个上游都由路由决定，`default` 只是兜底那一个。两个都不是照抄值，所以只从卡上拿掉，不做成图标说明也不摆行
2. **接口表**（`components/interface-table-card.tsx`）：**直接铺开**，不做收起——它是一张参考卡，用户来这一步就是为了看它，摆出「点一下才能看」只会白多一步。每行是方法 + **主写法**（`entry.paths[0]`，带 `/v1`）+ 一句它是什么 + 协议名。两条被有意拿掉：**等价写法**（不带 `/v1`）不铺第二列（服务端两种写法都受理，这件事写在卡头那句说明里；逐行列出来读起来像是要用户去挑一条，反倒把唯一的正解淹了）；**`GET /v1/models`** 不进表（它由本地直接应答、不转发上游，也不是「接上没接上」的证据，摆在这里只会被误读成「接口就这几个」）——渲染时用 `entry.protocol !== null` 过滤掉它。表的内容全部来自契约层的 `PROXY_INTERFACE_ENTRIES`（`packages/contracts/source/protocols.ts`），**不在页面里维护第二份路径清单**：它由 `packages/core/source/proxy/protocols/interface-surface.test.ts` 双向守着——契约里写下的每条（方法，路径）都必须在真实注册表里解析成声明的协议，注册表里每条协议路径也必须在契约里出现。**只收真正支持的接口**：注册表认得出旧版文本补全与文本向量（与对话补全同属 `openai-completions`），但上游地址是按协议配的，它们的正文没有对应的地址形态，转发出去只会落到一个聊天接口的地址上——「认得出」与「支持得住」是两件事，清单只承诺后者。这些不受理但认得出的路径在内核测试里各自留了名字（`UNEXPOSED_ROUTES`），多出一条路径必须有人做一次决定。
   - 客户端配置页顶部用的是**同一对组件**，地址卡传 `layout="cards"`（地址收进凹槽）。同一个事实有两处渲染就会有两处版式和两处「少写一条路径」的机会；两个页面各写一遍「这一行该叫什么名字」，迟早会在一处写出意译名
3. **不再有「查看请求记录」的收尾行**：引导第二步与客户端配置页都不再在接口卡底部摆一行「接上没接上」的说明加一颗跳转按钮。接口表只回答「支持哪些路径」，不承担「接上了吗」这个动作入口。

### 服务状态为什么不摆在这一步

服务状态（在不在跑、监听在哪、谁能连、去改监听地址）**不摆在引导第二步**。它是「服务本身」的事，不是「往客户端里填什么」这件事的一部分：服务没起来是一个全局前提，前面已经成立、也随时能在逻辑模型页页头与托盘菜单里看和改；把它做成一条状态带压在第二步顶部，只会让「怎么填」这一页多一层与当前动作无关的噪音。这一步要回答的只有一件事——把地址填到哪、怎么填。

监听 `0.0.0.0` 的说明（局域网别的设备也能连）同理拿掉：它挂在「服务状态」上，属于进阶用法而不是「填到哪里」的前提。展示给客户端的地址一律回落到 `127.0.0.1`（见 `@common/proxy-origin`），地址不全时地址位摆占位符并禁用复制，而不是整块消失——版面不跟着数据有无变形。

这一步的标题就是它的步骤名「接入工具」（`onboarding.step.configure.label`）：它要去掉的是「接不上」这件事，而不是这件事与哪张卡有关；那句话（「把工具指到这个地址」）留在这一屏自己的内容里讲，不占标题。

### 智能路由（路由工作台）

工作流图与规则表的编辑与试跑，页头标题后面跟一个模式切换器选当前生效的模式（同一时刻只有一种）：

- **工作流图**：节点图的编辑与试跑，产品口径、节点设计与默认策略见 [route-design.md](./route-design.md) §2–§4；
- **规则表**：从上往下匹配的规则清单，行上摆着名字、条件读法、落点与启停，改名与条件全在行内展开里改（输入带类型化提示语，落点是单选，逻辑模型在一个多选输入框里勾选、勾选顺序即优先级，再加一条条件是条件列末尾那个虚线空格子），排序只走拖拽，兜底落点单独一行、单独展开，新增规则是页头右上角的主按钮，语义见 [route-design.md](./route-design.md) §2.11。

两种模式各自一套正文、各自一个试运行抽屉——两个抽屉要回答的问题不同（图回答「这趟经过了哪些节点」，规则表回答「为什么是这一条」），因此文案与版面也各写各的。页头同样如此：标题写的就是当前模式的名字（工作流编排 / 路由规则），模式图标按钮跟在标题后面（点开的是那个全局的模式选择弹窗，设置页的「生效模式」是它的另一个入口），试运行按钮在两处叫同一个词。真正共用的不止页头版式与同一份示例请求：**保存按钮、保存弹窗与历史版本菜单在两个模式里也是同一套**（规则表的保存会把整张表发布成一个新版本、旧版可回滚，量词换成「几条规则」、说明文案换成规则表那一份）。图模型、控制流与持久化见 [workflow-engine.md](./workflow-engine.md)。

## 用户流程

### 首次使用

1. 启动应用，菜单栏/托盘出现图标
2. 引导第一步建第一个供应商（页面摊开一张预设卡片墙，首张是「自定义供应商」；已有供应商时则从表格下方同一张宫格进），再从它那一行点「添加模型」拉取并勾选；一个供应商都没有时这里只给一句「还没有供应商，选一个，建起第一个」。选路不单独成步：内建默认已经在下，想比较或改的人去「路由」页
3. 在逻辑模型页把模型拖成想要的顺序，启停不想参与路由的项；可继续添加多个模型
4. 引导第二步给出本机服务的那一条地址（带不带 `/v1` 都受理，页面上只说一条），紧接着是就地嵌入的配置编辑器：选一个在用的工具，在它「配置内容」卡头右边按「生成配置」（按内置默认模型改写）再按「保存内容」把这份配置改成指向本机服务，改错了「撤销改动」；登记表里没有的工具，就把这条地址照抄进它正在用的客户端
5. 第二步往下依次是地址卡、配置编辑器与接口表（单列排布）：接口表直接铺开，只列会被转发上游的三条接口、只写带 `/v1` 的主写法；不再有服务状态带，也不再有任何「查看请求记录」的收尾行
7. `model` 可保留客户端原有的任意非空值，代理会通过 `default` 逻辑模型处理，并在转发时替换为当前 ProviderModel 的 `modelName`；API Key 同理，填任意非空字符串即可
8. 从客户端发一条消息，在请求记录里看到这条请求就说明链路已通，控制台里显示尝试过程和切换路径

### 日常使用

1. 应用在后台运行，可选开机自启
2. 托盘菜单第一行与悬停提示反映代理是否在运行（图标本身不表达状态）
3. 临时禁用某个供应商或调整优先级
4. 查看请求日志了解每次请求经过了哪些供应商、在哪里失败、最终由谁成功

## 路由与工作台

路由工作台是代理策略本体的编辑入口：请求怎么被识别、怎么判定、落到哪个逻辑模型，全部表达为一份**可编辑且可版本化的定义**——工作流图或规则表，代理运行时执行的就是当前生效的那一版。这些内容各自只有一个权威落点，本文不再重复：

- **产品语义**（两种模式的划分与规则表语义、`route` 输出契约、路径取值与比较操作符、默认「模型直达」策略、四个策略预设）：见 [route-design.md](./route-design.md) §2
- **引擎与图模型**（节点/边结构、控制流与端口、迭代、脚本与 LLM 能力注入、图的加载与保存）：见 [workflow-engine.md](./workflow-engine.md)
- **画布交互与节点面板**：见 [route-workbench.md](./route-workbench.md)

契约以代码为准：图模型与节点定义在 `packages/contracts/source/router/types.ts`，落库结构在 `packages/core/source/database/config-schema.ts`（`workflows` 表在配置库里）。
