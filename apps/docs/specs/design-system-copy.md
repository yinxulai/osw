## 1. 语气：从 1931 条里实测出来的四条

### 1.1 中文侧的实际特征（`[源码]` 频次统计）

| 特征 | 实测 | 结论 |
| --- | --- | --- |
| 敬语"请" | **286 次** | **"请"是主要的礼貌手段**："请检查 API Key 是否正确"、"请先给模型填写自定义地址" |
| 敬语"您" | **0 次** | **不用"您"**。osw 是给开发者用的本机工具，敬语靠"请"而不靠"您" |
| 人称"你" | 10 次 | 极少用。**默认不出现人称**（"保存失败"而不是"你的保存失败了"） |
| "我们" | 1 次 | **基本不用第一人称**。产品不自称 |
| "无法" | 24 次 | 能力缺失用"无法"（"无法连接到本地服务"），不用"不能""不可以" |
| "失败" | 83 次 | 动作失败用"失败"（"上游请求失败"）。**这是最高频的失败表述** |
| "出错" | 2 次 | 只用于界面级异常（`common.error.pageTitle` 等），不用于业务失败 |
| 感叹号 | **2 次** | **不用感叹号**。任何"！"都要有理由 |

### 1.2 英文侧的特征

| 特征 | 实测 | 结论 |
| --- | --- | --- |
| 大小写 | `Select all` / `Copy failed` / `This page crashed` | **句子式大小写（sentence case）**，**不用 Title Case** |
| 标点 | 按钮标签不带句点（`Cancel` / `Retry`）；句子带句点（`It has been contained, so the rest of the app keeps working.`） | 短标签无标点，完整句子有标点 |
| 人称 | `Cannot reach the local service`（无主语） | **与中文一致：不出现人称** |
| 逗号连接 | `…credentials, check the API key` | 英文用**逗号**连接"陈述 + 建议"，中文用**逗号或冒号** |

### 1.3 四条规则

| # | 规则 | 说明 |
| --- | --- | --- |
| 1 | **陈述事实，不评价、不道歉、不鼓励** | ❌"哎呀，出错了" ❌"抱歉，操作失败" ✅"保存失败"。感叹号只有 2 处，**保持住** |
| 2 | **不出现人称** | 中文无"你/您"、英文无 "you"。唯一例外是**必须指明"谁"**的场合（如"这些模型会一起失去该协议"里的"这些模型"是名词不是人称） |
| 3 | **礼貌靠"请"，且"请"只出现在可执行的建议前** | ✅"请检查 API Key 是否正确"（给了动作）❌"请稍后重试"（等于没说，且"稍后"没有信息量） |
| 4 | **产品不自称** | 不用"我们""本产品""OSW 会…"。要指代产品时说"本地服务"（`errors.NETWORK_ERROR` 就是"无法连接到本地服务"） |

## 2. 长度：按位置给上限

长度的下限不是问题（p50 = 18 字），**上限才是**。按使用位置：

| 位置 | 上限 | 依据 / 现有例子 |
| --- | --- | --- |
| **按钮** | **4 个汉字 / 2 个英文单词** | `取消` `删除` `重试` `刷新` `全选`；`Cancel` `Retry` `Select all`。**超了就不是按钮文案** |
| **状态标签** | **4 个汉字** | `运行中` `已停止` `已停用` `已删除` `未知` |
| **表格列头** | **6 个汉字** | `供应商模型` `协议` `传输` |
| **行内提示 / Tooltip** | **40 字** | `点击此列表头排序`（8 字）。Tooltip 在被读之前就消失了，超过 40 字没人读完 |
| **字段说明（hint）** | **80 字** | p90 = 69 落在这里。**超过 80 字应改成说明文档 + 链接** |
| **错误描述** | **120 字** | 现有最长错误 `errors.ENDPOINT_URL_IN_USE` = 230 字，**它是特例**（需要在确认框里讲清"会导致哪些模型一起失效"），见 §3.3 |
| **确认框描述** | **200 字** | 用户在这里**必须读完才能决定**，所以可以长。但要分段 |
| **空态标题 / 描述** | 标题 12 字 / 描述 40 字 | 空态是"看到就能走开"的位置 |

**样式表**：同一个 key 的中英文长度**允许差异 ±40%**——1080 个宽度的差异是布局必须容忍的。
**不要**为了让英文更短而删信息，**也不要**用 `min-w` 硬撑：

> **按钮/标签的宽度不能被文案撑开。** 文案超长时先改文案，再看能不能截断
> （见 [`design-system-typography.md`](./design-system-typography.md) §7），**最后**才考虑放宽容器。

## 3. 出错文案的写法

### 3.1 三层分工（机制在 [`i18n.md`](./i18n.md) §5，这里只讲怎么写）

```
错误码（机器契约，稳定，不翻译）
   ↓ 界面按错误码本地化
errors.<CODE>（用户可见文案，进目录）
   ↓
英文诊断原文（详情面板里原样显示，永不翻译）
```

**规则**：

| # | 规则 |
| --- | --- |
| 1 | **toast / 提示用本地化文案**（`errors.<CODE>`） |
| 2 | **详情面板 / 诊断结果保留英文原文**——排障时要能搜索、能贴给上游 |
| 3 | **不要设 `errors.UNKNOWN`**：目录里没有的错码**直接退回英文诊断原文**（[`i18n.md`](./i18n.md) §5 目标契约第 4 条）。给一个叫"未知错误"的兜底会让所有未覆盖的错码长成一样，反而掩盖问题 |
| 4 | 新增错误码**不补文案就编译失败**（`Record<ApiErrorCode, …>`），所以"忘了翻译"不是可能的状态 |

### 3.2 一条错误文案的骨架

**能给出动作的，必须给出动作。** 两段式：

```
<发生了什么>，<可以做什么>
```

现有样例（`[源码]`）：

| Key | 文案 | 结构 |
| --- | --- | --- |
| `errors.UPSTREAM_AUTH_FAILED` | 上游拒绝了认证，**请检查 API Key 是否正确** | 陈述 + 动作 ✅ |
| `errors.UPSTREAM_MODELS_UNAVAILABLE` | 无法从上游获取模型列表，**请检查地址与协议是否匹配** | 陈述 + 动作 ✅ |
| `errors.NETWORK_ERROR` | 无法连接到本地服务 | 纯陈述（**用户能做的只有重启应用，不需要写进文案**） |
| `errors.INTERNAL_ERROR` | 服务内部错误，**请查看运行日志** | 陈述 + 动作（指向日志） ✅ |
| `errors.NO_AVAILABLE_PROVIDER` | 该逻辑模型没有已启用且可用的供应商模型 | 纯陈述（动作在界面上下文中已有） |

**规则**：

| # | 规则 |
| --- | --- |
| 1 | **动作必须是用户真能执行的**。❌"请联系管理员"（本机工具没有管理员）❌"请稍后重试"（没给信息） |
| 2 | **不要暴露内部结构**：不写类名、表名、文件路径、堆栈。这些留给详情面板 |
| 3 | **不要用错误码当文案**：`errors.ALL_PROVIDERS_FAILED` 是"所有上游供应商都失败了"，不是"ALL_PROVIDERS_FAILED" |
| 4 | **不要写"未知错误"**：真不知道就退回英文原文（§3.1 规则 3） |
| 5 | **失败原因用 `failureReason.<CODE>` 的短标签**（`超时` / `限流 (429)` / `服务错误 (5xx)` / `认证失败` / `其他`）——它们出现在**表格单元格**里，必须极短 |

### 3.3 长错误文案的例外：`errors.ENDPOINT_URL_IN_USE`

这是全仓最长的错误文案（**230 字**），值得单独看，因为它是"长文案该怎么写"的范例：

> 供应商「{providerName}」的 {protocols} 协议还有 {count} 个模型在用（{models}）：
> 这里没有可用的地址，这些模型会一起失去该协议，请先给模型填写自定义地址，或者保留这个地址

它做到的四件事：

| # | 做法 |
| --- | --- |
| 1 | **指名道姓**：用 `{providerName}` / `{protocols}` / `{count}` / `{models}` 把具体对象填进去，不是"该供应商" |
| 2 | **说清后果**：**"这些模型会一起失去该协议"**——用户不知道后果就无法权衡 |
| 3 | **给两个选项**：填写自定义地址 / 保留地址。用"或者"明确是二选一 |
| 4 | **用引号包住用户数据**：「」包住供应商名，避免和正文糊在一起 |

**规则**：**错误文案超过 80 字时，必须包含"后果"**。只描述现象的长文案是流水账。

### 3.4 危险的确认框

删除类操作的确认文案要写**后果 + 对象**，不是"确定要删除吗？"：

| # | 规则 |
| --- | --- |
| 1 | 标题说动作（"删除规则"），描述说**后果**（"删除后无法恢复，依赖它的路由会失效"） |
| 2 | 危险动作的按钮**用动词**（"删除"），不用"确定"。`ConfirmDialog` 的 `confirmLabel` 就是为此存在的，默认值是 `common.confirm.confirmLabel` = "确认" |
| 3 | 不可恢复的操作要明说"无法恢复" |

## 4. 标点

`[源码]` 频次：`（）` 117 处、`、` 91 处、`；` 67 处、`「」` 45 处、`…` 28 处、`“”` 14 处。

| # | 规则 | 依据 |
| --- | --- | --- |
| 1 | **中文用全角标点，英文用半角** | 目录分语言文件，天然分开 |
| 2 | **中文引号用 `「」`（45 处），不用 `""`** | `“”` 的 14 处与之并存 → **这是不一致，应统一到 `「」`**。`「」` 在中文里更清晰（`“”` 与英文引号在等宽字体下难区分） |
| 3 | **用户数据用引号包起来** | 「{providerName}」——避免用户输入的内容与正文粘在一起 |
| 4 | **省略号用 `…`（28 处），不用 `...`** | 中文排版的标准形式（`common.action.saving` = "保存中…"） |
| 5 | **列表分隔符进目录** | `common.listSeparator` = "、"（中文）/ 英文对应不同符号。**不要在代码里拼 `join('、')`** |
| 6 | **并列用 `、`，分句用 `；`，不用逗号串长句** | `；` 67 处说明这是既定做法 |
| 7 | **括号内的补充不构成完整句子时，句号在括号外** | — |
| 8 | **不用感叹号** | 全仓只有 2 处 |
| 9 | **按钮/标签末尾不加标点** | `取消` / `Retry` |
| 10 | **书名号/代码标记**：字段名、类名用**反引号或 `「」`**，不用 `""` | 目录是纯文本，反引号会被原样渲染 → **用 `「」`** |

## 5. 术语：同一件事只有一个说法

`[源码]` 实测的高频术语，**中英对照固定如下**。新增文案必须沿用，不得另造同义词：

| 概念 | 中文 | 英文 | 不要写成 |
| --- | --- | --- | --- |
| Provider | **供应商** | provider | 服务商 / 渠道 / 提供方 |
| ProviderModel | **供应商模型** | provider model | 渠道模型 / 上游模型 |
| Logical Model | **逻辑模型** | logical model | 虚拟模型 / 聚合模型 |
| endpoint | **端点 / 地址** | endpoint | 接口 / 链接 |
| protocol | **协议** | protocol | 格式 |
| route | **路由** | route | 规则（那是 rule） |
| rule | **规则** | rule | 策略 |
| attempt | **尝试** | attempt | 重试 / 请求 |
| failover / switch | **切换** | switch | 转移 / 故障转移 |
| request log | **请求记录** | request log | 日志（那是 log） |
| proxy | **代理** | proxy | 中转 |
| quota | **配额** | quota | 额度 |

**规则**：

| # | 规则 |
| --- | --- |
| 1 | **英文术语不翻译**：API Key、JSON、SSE、Base URL、Token 在中文文案里保持原样（`errors.UPSTREAM_AUTH_FAILED` 就写"请检查 API Key 是否正确"） |
| 2 | **"供应商"与"渠道"不是同义词**，代码里只有 Provider → **统一说"供应商"** |
| 3 | **"日志"与"请求记录"是两个页面**（`logs` / `requestLogs`），不要混用；除非明确指日志文件，否则说"请求记录" |
| 4 | **用户数据原样展示，绝不翻译**：供应商名、模型名、规则名、描述、请求正文、上游错误文本（[`i18n.md`](./i18n.md) §4「不进入 UI 目录的内容」） |

## 6. 其他：数字、日期、复数

规则在 [`i18n.md`](./i18n.md) §4，此处只列界面侧的三条：

| # | 规则 |
| --- | --- |
| 1 | **数字不进目录**，用 `Intl.NumberFormat` 按当前 locale 格式化（中文的千分位与英文不同） |
| 2 | **日期不进目录**，用 `Intl.DateTimeFormat`。日志时间戳的格式定义在 `logs-table.tsx` 的 `formatTimestamp`（`hour12: false` + 毫秒） |
| 3 | **不拼接句子**：整句作为一条消息，用 `{placeholder}` 传参。复数走 `Intl.PluralRules`，中文用单串 |

## 7. 落地清单

写或改一条用户可见文案时逐条过：

- [ ] 它进了 `packages/contracts/source/i18n/catalogs/`（不是硬编码）——`no-hardcoded-cjk` 会拦
- [ ] 中文与英文**同时**写了（英文目录是结构真相源，缺 key 编译失败）
- [ ] 按钮 ≤4 汉字，状态标签 ≤4 汉字，hint ≤80 字
- [ ] 没有感叹号，没有人称，没有产品自称
- [ ] 有建议时用"请 + 可执行的动作"，且动作用户真能做
- [ ] 错误文案说清**发生了什么**；超过 80 字时说清**后果**
- [ ] 没有暴露类名、表名、路径、堆栈
- [ ] 没有 `errors.UNKNOWN` 这类兜底文案
- [ ] 术语与 §5 表一致（供应商 / 供应商模型 / 逻辑模型 / 请求记录 / 切换 / 尝试）
- [ ] 用户数据用 `「」` 包住
- [ ] 标点用全角，省略号用 `…`，引号用 `「」`
- [ ] 数字/日期用 `Intl.*`，没有写进目录
- [ ] 英文用 sentence case，短标签不带句点

## 8. 未核实项

| 项 | 状态 | 为什么 |
| --- | --- | --- |
| **`「」` 与 `“”` 的取舍是否有意** | `[未核实]` | 两者并存（45 : 14）。本文**建议统一到 `「」`**，但无法判定 `“”` 的 14 处是"较早的写法"还是"刻意的分场景用法"。**未逐条看**那 14 处 |
| **中英文长度 ±40% 这个容忍度是否够** | `[未核实]` | 本文按 p50/p90 的差值推算，**没有在真实布局里验证过**英文最长那几条会不会撑破容器（英文 max = 311 字符，比中文 max = 259 更长） |
| **"我们"1 次与"你"10 次的具体位置** | `[未核实]` | 只统计了次数，**没有逐条看**它们是否属于合理例外（如 native 层的主进程对话框）。若其中有不合理的，本文的"不出现人称"规则需要补例外清单 |
| **`请稍后重试` 这类无信息量的建议是否存在** | `[未核实]` | 本文把它列为反例，但**没有全量扫描**目录里是否真有这种写法 |
| **语气的一致性是人工审校过的还是自然形成的** | `[未核实]` | 1931 条文案的语气高度一致（无感叹号、无第一人称），这**可能**是有意约定，**也可能**是作者群小导致的自然结果。仓库里没有找到成文的用语规范 |
| **`failureReason.*` 与 `errors.*` 的完整对应关系** | `[未核实]` | 两者都有 `AUTH_FAILED` 等条目但语义不同（一个是失败原因短标签，一个是错误码文案）。**是否存在重复或应合并，未核实** |
