# 安全与隐私

## 安全边界

### 网络隔离

- 服务默认绑定本机回环地址 `127.0.0.1`，默认不暴露到局域网
- `listenHost` 可由用户在设置中修改；支持改为 `0.0.0.0` / `::` 绑定所有网卡以暴露给局域网 / WSL / 容器，属于用户显式选择，用户需自行依赖操作系统防火墙控制入站访问
- 管理接口**不校验 `Host`**：门是凭证（下一节），`Host` 挡不住任何拿着凭证的调用方，也救不回任何已泄漏的凭证，只剩「用局域网 IP 打开控制台就上不去」这类故障。唯一的回环判据在**注入凭证**那一刻：静态托管只把 `window.__OSW__` 写进「`Host` 指向回环」的那份入口 HTML，因为 DNS rebinding 的页面与本服务同源、读得到我们发回的响应体——不把凭证发出去，它的每次 API 调用就都是 `401`（`management/gateway/loopback.ts`、`management/gateway/console-host.ts`）
  - 请求仍然能拿到页面本身（前端产物本来就是公开的），只是没有凭证
- 代理入口（`/v1/*`）同样不看 `Host`：它面向的是任意调用方，那里的边界是「监听在哪里」

### 访问控制

管理接口与代理入口是两套边界，不能混为一谈：

- **代理入口**（`/v1/*` 等）：面向用户的调用方，**不校验调用方身份**。本软件不向下签发任何调用方 API Key——客户端在 `Authorization` / `x-api-key` 里填什么都不影响能不能调通：那些头只会被脱敏后写进日志，并在转发时换成渠道自己的密钥（见下方「密钥存储」）。因此「谁能用这个代理」完全由**它监听在哪里**决定：
  - 监听在回环（默认 `127.0.0.1`）时，本机任意进程与任意网页都能调它——同源策略只挡「读响应」、不挡「发请求」；
  - `listenHost` 改成 `0.0.0.0` / `::` 时，同网段任何设备都能调它，直接消耗用户的渠道额度；
  - 要不要向下签发调用方 API Key 属于未完成项，见 [roadmap.md](../roadmap.md) §7。
- **管理接口**（`/api/*`）：只服务于本进程自己的控制台，**每次应用启动随机生成一份凭证**（`management/token.ts`），**每一条请求都必须带上** `x-osw-token`，否则 `401`。
  - 凭证是 32 字节随机数的 base64url。**由宿主（桌面主进程 / 命令行进程）在应用启动时生成一次**，经 `RuntimeConfig.managementToken` 交给 core；core 只负责校验，自己不生成——因为 core 的 `startServer()` 不等于一次应用启动：桌面形态的服务跑在独立进程里，崩溃后会被宿主重启（`server-host.ts` 的重启预算），若凭证跟着它重算，主进程手里那份立刻作废，渲染层随后的每次请求都会 `401`。同理，它与代理是否启动无关。
  - **凭证没有例外**：不区分浏览器还是本机进程。曾经有过一个「只卡浏览器」的版本，判据是 `Origin` / `Sec-Fetch-Site`——而这两个头是**调用方自己写的**，任何本机 `curl` / `fetch` 不发它们就跳过了校验，`/api/provider/export`（`includeApiKeys: true`）因此对本机任意进程敞开。把门锁交给被拦的人不算门，所以这条判据被整个删掉了（`management/gateway/access.ts`）。
  - **开发形态不校验凭证**：`environment === 'development'` 时整条凭证检查被跳过（`gateway/access.ts` 的 `requireCredential: false`，由 `gateway.ts` 传下来），路径与方法判据一字不变。理由是开发期前端不是宿主加载的——Vite 页面、调试脚本、自动化脚本都拿不到 `window.__OSW__`，每条请求都要先去数据目录读 `management.token`，自动化开发直接卡住；而开发形态用的是独立数据目录（`@common/runtime-profile`），放宽它碰不到用户的数据。代价是开发实例上本机任意网页都能调 `/api/*`，这个取舍是明确的。
  - **交付通道是一个 `0600` 的文件**：`<dataDir>/management.token`，由管理服务在 listen 成功后写入、退出时删除（`management/token-file.ts`、`management/server.ts`）。写失败就让启动失败：一个「起得来但停不掉」的进程比一次启动失败更难收拾。
  - 它**不写进 `runtime.json`**：那份快照会被 `status --json` 原样打到标准输出，凭证混在里面就等于进了 shell 历史、管道和用户的截图。分开一个文件，「给人看的快照」与「给程序用的秘密」各走各的路。
  - 比较走 `crypto.timingSafeEqual`（长度先比一次，长度是固定值，从协议文档就能知道，不构成泄露）。
  - 边界要说清：它挡得住**本机浏览器里的网页**、沙箱内的应用、容器/WSL 里能连回环但读不到数据目录的进程、以及**同机其他用户**（`0600` 只给属主）。它挡不住**同一用户的**本机进程——那类进程本来就能读数据目录、改配置，这不是疏漏，是边界本身的形状。
  - 为什么需要它：**「只监听回环」不是访问控制**。本机任意网页都能向 `127.0.0.1` 发请求，`Content-Type: text/plain` 的「简单请求」甚至不会被预检拦住，于是 `/api/provider/export` 这样的接口就是一条把明文密钥读走的通路；而同机其他用户连伪造头都不用，回环 TCP 对他们是可达的。
  - 管理接口固定监听回环（`managementHost` 由宿主固定为 `127.0.0.1`，没有对用户暴露的开关，CLI 的 `--host` 只作用于代理）。
  - **开发形态不再有凭证读取口**：曾经有个 `POST /api/development/management-token`，前提正是「凭证只活在内存里」。凭证改成无条件校验之后，一个把凭证发出去的接口只能是绕过校验的后门，因此被整个删掉了。开发形态现在干脆不校验凭证，也就更不需要这个接口。
- **凭证怎么到页面**：桌面形态由主进程通过 preload 注入（`window.__OSW__.apiToken`，主进程自己就是生成方，不靠服务回报）；命令行 `--web` 形态下页面本来就是管理服务自己发的，入口 HTML 在被送出时被注入同一行脚本（`management/gateway/console-host.ts`，入口文件带 `no-cache`，不会被缓存下来）。两条路给页面的是**同一个值**——也就是磁盘上那份，页面不自己读文件。页面侧仍然不写 `localStorage`：凭证每次启动都会变，缓存一份只会让下一次启动读到废值。
  - **例外**：`pnpm dev:preview` 直接在浏览器里开 Vite 产物，等不到宿主注入，拿不到凭证；但开发形态的管理服务不校验凭证，所以它照样能调通，可直接用来调界面与接口。
  - **无头截图**（`pnpm screenshots`）是另一个 Electron 进程，页面同样是**真浏览器**，所以它必须拿到凭证；它自己从数据目录里读 `management.token`（`apps/app/source/screenshot-export-entry.ts`）。读文件在这里是安全的：那个进程从不 `app.setPath('userData', ...)`，读一个文件不会把它的 Electron 配置目录带偏。
- **跨域**：管理接口回显请求带来的任何 `Origin`（没有来源时回 `*`），并回显预检里 `Access-Control-Request-Headers` 问的那一份头。**这里没有任何名单**。
  - 原因很直接：CORS 只决定浏览器允不允许页面**读响应**，它从来不是防线——真正的门是凭证。而名单只会制造故障：开发期换了个端口、用局域网 IP 打开控制台、将来多加一个自定义头，每一样都要回来改服务端。
  - 允许的方法是 `POST, OPTIONS`（`/api/*` 全部是 POST，`GET` 一律 `405`）；预检没问任何头时回 `*`。来源变化时响应头也跟着变，所以必须带 `Vary: Origin`。
  - 预检在凭证检查**之前**短路成 `204`：预检是浏览器自己发的，它既不可能带自定义头，也不该被要求带。
- **无凭证时的预期行为**：正式形态下所有 `/api/*` 一律 `401`，没有例外、没有「本机进程」这条旁路。宿主没把凭证交下来属于配置异常，这时同样 fail-closed（`access.ts` 对 `null` 直接回 `false`）——一个漏配的环境不能静默变成一个对本机任何进程可写的环境。开发形态不校验凭证（见上一节）。

### 单实例

- 桌面、命令行、容器三种形态都只允许一个实例持有同一个数据目录；互斥由 core 的 `runtime/instance-lock.ts` 提供，属于**基本能力**，不是某个宿主的补丁：
  - 锁文件是数据目录下的 `instance.lock`，记录持有者 pid、启动时间与心跳时间；
  - 判定持有者是否活着，既看 pid 还在不在，也看心跳新不新鲜，因此 pid 被操作系统复用不会把死实例误判成活实例；
  - 心跳由 `startInstanceLockHeartbeat` 周期续写，宿主崩溃后残留的锁会被下一个实例判定为遗弃并接管；
  - 换端口换不掉它：锁挂在数据目录上，不在端口上。
- 桌面形态在这之上还有一层操作系统级的 `app.requestSingleInstanceLock()`：第二次启动不新开进程，而是把已有窗口唤到前台。

### 路由脚本沙箱

路由工作台的 JS 脚本节点在服务端进程内的 `node:vm` 沙箱里执行用户源码，边界如下：

- 沙箱里只有三样东西：`payload`（本次运行 payload 的**深拷贝**）、`get(路径)`（只读取值）与 `console`（日志回传 trace）；
- 没有 `require` / `import` / `eval` / `Function`：`codeGeneration.strings = false`，脚本无法再生成新代码；
- 没有网络与文件系统 API：沙箱不注入任何宿主对象，脚本只能操作内存里的那份数据；
- 有限时：节点可配超时（上限 10s），超时即中断并把失败原因写进 trace；
- 脚本改动不会污染引擎正在使用的决策数据（传的是深拷贝），失败也不阻断整张图执行；
- 脚本内容属于用户配置，随工作流图的版本一起保存在本地，不随请求日志外发（规则模式没有脚本节点）。

### 路由 LLM 节点的出站调用

路由工作台的 LLM 节点会发起真实上游请求，因此：

- 调用**复用逻辑模型自己的上游通路**（供应商、协议、密钥、故障转移），不新增密钥存储位置，密钥仍在主进程 / 密钥环里，不进渲染进程；
- 提示词与回复只在本地参与运行时数据，写回 payload 的只是回复文本；
- 出站请求路径与普通代理请求一致，同样受出站代理设置与日志脱敏规则约束，详见 [outbound-proxy.md](../proxy/outbound-proxy.md)。

## 密钥存储

- Provider API Key 不写入明文配置、日志或导出的供应商包（除非用户显式选择包含）
- Provider API Key 使用 Electron `safeStorage` 或系统密钥环（macOS Keychain / Windows Credential Manager / Linux Secret Service）存储
- 数据库中仅保存 Provider API Key 的密钥引用 ID
- 供应商包默认导出脱敏版本（不含明文 API Key）；包含明文必须由用户显式勾选，并在界面提示该文件等同于凭据，详见 [provider-model.md](../data/provider-model.md)
- 自定义上游代理 URL 例外：允许携带账号密码，并作为普通设置写入 SQLite；代理设置不进入供应商包，日志、错误与测试结果仍必须脱敏，详见 [outbound-proxy.md](../proxy/outbound-proxy.md)
- 云同步的凭据（Gist 上是 GitHub 令牌）与 Provider API Key 同一套设施：只存进宿主密钥库，按后端各存一份且引用固定，不写入 SQLite、日志或任何导出文件；数据库里只留当前承载方式、账号名、远端句柄与两个同步时间戳，详见 [cloud-sync.md](../data/cloud-sync.md)

## 隐私策略

### 遥测

- 使用统计**默认开启**：匿名上报统计数据用于改进功能，界面上不提供任何入口（不设开关、不设设置模块、也不做提示）；完整口径（事件白名单、匿名标识、上报链路）见 [telemetry.md](./telemetry.md)（口述口径见 §3，自查走管理接口的预览）
- 统计链路是**唯一**被允许出站的非模型流量：它直连自建端点，不在客户端直接打到任何第三方分析服务，也不走用户的出站代理设置
- 除它之外不存在任何形式的遥测：没有崩溃上报、没有行为埋点、没有远程配置拉取

### 数据本地化

- 所有配置、密钥、日志保存在用户主目录下的隐藏目录，位置不随平台变化
- 不向任何第三方服务器上传用户数据；唯一例外是默认开启的匿名使用统计，它不携带任何用户内容（见 [telemetry.md](./telemetry.md)）。统计只发固定枚举、布尔与分桶，没有任何位置能随手塞进一段内容——**包括模型名在内**（理由见 [telemetry.md](./telemetry.md) §3）；其中关于「处理了多少任务」的那一条只报「成功处理了一次」，不带任何属性，也不含耗时、Token 或状态码
- 配置云同步是用户主动触发的例外：数据发往**用户自己的**第三方云存储（当前是 GitHub Gist），由他本机直连完成，我们不参与也不中转（同一条判断见 [outbound-proxy.md](../proxy/outbound-proxy.md) 对统计链路的说明）。快照整份只做 base64 编码，**这是编码不是加密**，而快照里带着各供应商的 API Key——「换台机器拉一次就能用」正是靠这一点成立。同时这种「私密 Gist」也不是加密存储：GitHub 及其运维方在技术上能读到内容。因此这条通路的定位是「用户自己信任的容器」，不是安全的密钥仓库，这一点在各处文档里写明（见 [cloud-sync.md](../data/cloud-sync.md)）
- 代理仅转发用户请求到用户配置的 Provider 供应商

### 请求与响应数据

- 默认保存完整请求体和响应体，以便直接进行请求调试和故障分析；用户可在设置中关闭正文记录
- 日志同时记录元数据：时间、模型、协议、供应商、状态码、耗时、错误摘要
- 客户端请求、最终响应、每次 Provider 尝试，以及协议转换前后的内容均视为敏感本地数据
- 记录前必须脱敏 Authorization、API Key、Cookie、Set-Cookie 等敏感头；正文内容完整保存在本地数据库，正文自身不视为已脱敏
- 请求与响应都**不设大小上限**：能通过守卫调用管理接口的一方本来就能改配置、导出密钥（凭证见「访问控制」），给它再插一道大小闸门挡不住任何我们假定可信的人；代理接口拒「大正文」等于替用户决定他的多模态请求能有多大，`core-network` 的缓冲取正文也一并去掉了那个上限参数。代价要说清楚：正文会完整读进内存并落库，内存与本地存储占用随请求量增长；这是本地工具的自担选择，不做资源消耗攻击假设（同一条判断见 [request-rewrite-rules.md](../proxy/request-rewrite-rules.md)）
- 采集与保留是两个独立维度：请求日志与请求响应正文各有一个开关、各有一个自动保留天数（请求日志默认**永久保留**，正文默认 **7 天**）；关闭开关只影响后续采集，不删除已有数据
- 清理分两种粒度：按请求日志保留天数清理会级联删除该请求的正文、尝试记录与用量行；只按正文保留天数清理则只删除正文（含协议转换前后两个视角），请求行、尝试行与指标保留，历史统计不失真
- 手动“清理历史日志”支持分别输入两个保留天数后即刻执行，不改动自动保留设置
- 内容查看和导出都应明确提示可能包含提示词、文件内容和模型输出；导出默认不包含正文
- 日志内容只保存在本地数据目录，不上传任何第三方服务器

## 本地数据位置

数据目录是 `<用户主目录>/.osw`（开发档 `.osw-development`），三个平台同一规则，见 [packaging.md](../platform/packaging.md) §5.5：

| 文件 | 内容 | 丢了会怎样 |
|------|------|------|
| `config-v1.db` | 供应商、模型、路由、改写规则等用户配置 | 不可再生，**值得单独备份** |
| `data-v1.db` | 请求日志、正文、用量、运行时日志与健康状态 | 只丢历史统计，代理照常工作 |
| `secrets.json` | 桌面形态的 API Key 密文与主密钥（主密钥也可放系统钥匙串） | 需要重新录入 API Key |
| `secrets.cli.json` / `secrets.cli.key` | 命令行形态的密钥文件 | 同上 |
| `telemetry-id` | 匿名使用统计的本地安装标识（仅在开启统计后生成） | 等同于换一台新设备，统计上重新计数（见 [telemetry.md](./telemetry.md) §4） |

两个数据库文件的职责边界与分库理由见 [data-model.md](../data/data-model.md) §2.1。两个形态的密钥文件刻意不同名：密文算法不同，同名同址会让后写的那个把前一份条目全部作废（见 [packaging.md](../platform/packaging.md) §5.1）。想只保留配置、清空历史，删掉 `data-*.db` 即可——下次启动会重建一个空文件。
