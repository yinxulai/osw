# 渠道诊断

## 1. 文档状态与边界

本文定义「测一下这条渠道到底通不通、有多快」这件事的产品与技术契约。

已实现：服务端队列里的 `model-test` kind（`packages/core/source/management/tasks/kinds/model-test.ts`）、草稿连接测试 `POST /api/model/connectivity-test`、控制台外壳上的非模态诊断浮窗、`packages/core/source/management/diagnostics/` 下的领域模块。

**交付机制不在本文。** 渠道诊断是一次「一批要真跑、有进度、能取消、结果要能边跑边看」的任务，它挂在通用任务队列上：入队、并发、去重、取消、推送的契约见 [task-queue.md](../overview/task-queue.md)。本文只说**诊断本身**——请求怎么写、可测目标怎么规划、结论怎么汇总。

**诊断不是代理请求。** 它借道代理执行链打一次真实上游请求（走同样的地址解析、同样的鉴权头、同样的出站代理），但它的目的只是拿一个结论回来给人看，不服务任何客户端。这个区别决定了本文后面所有的口径。

本文不覆盖：出站代理本身的配置与连通性（见 [outbound-proxy.md](../proxy/outbound-proxy.md)）；上游失败如何影响健康冷却（见 [observability.md](./observability.md)）；遥测事件的白名单与命名规则（见 [telemetry.md](./telemetry.md)）。

## 2. 两个入口

「测一下」有两个入口，它们看起来像同一件事，实际上**测的对象不同、副作用不同**。把它们合成一个接口是这类功能最常见的错误，因为合并的那一刻必然要在某个方向上撒谎：要么让草稿测试写库，要么让渠道诊断不记账。

| | 渠道诊断 | 草稿连接测试 |
|---|---|---|
| 接口 | `POST /api/tasks/enqueue`（kind `model-test`） | `POST /api/model/connectivity-test` |
| 测的是什么 | **已经保存的**那一份配置 | 表单里**还没保存的**那一份草稿 |
| 一次测几个 | 入队一批，队列按 `keyOf` 去重后逐个跑 | 这次要提交的那几行端点 |
| 走代理执行链吗 | **走** | **不走** |
| 结果进观测吗 | **进**（请求日志、用量、健康冷却） | **不进**（不写任何库） |
| 测协议转换吗 | 测（原生端点优先，无原生时用可转换端点） | 不测（按端点自己的协议发原生请求） |

**为什么草稿测试不进执行链、也不写库。** 草稿还没落库，没有 `providerModelId` 可挂，也没有「这个端点服务过一次真实请求」这个事实可以记——一次握手既不该累积用量，更不该把用户从没启用过的端点推进冷却队列。代价是它只测原生连通性，转换适配器、改写规则、故障转移这一整套在这里一件都用不上。用户问的是「这条地址配得对不对」，这个口径答的就是它。

**为什么渠道诊断走执行链。** 因为它要回答的是「真实请求会不会通」。地址怎么从「模型级覆盖 → 供应商级协议端点」两层里选出来，只能有一个答案；自己再拼一份 URL 等于给「诊断通过但真实请求打不通」留了条后门。所以目标规划复用 `proxy/planners/target-planner.ts` 的 `buildUpstreamTarget`，执行复用 `proxy/execution/attempt-executor.ts`。

两个入口共用 `diagnostics/probe-request.ts` 拼请求体——它们要回答的是同一类问题，请求写法不该有两份。这个模块原先长在渠道诊断的路由文件里，草稿测试反过来 import 另一个路由文件；现在它住在两侧都能依赖的位置。

## 3. 一次探测怎么发

### 3.1 请求体

三种协议各一种写法，由 `buildDiagnosticBody` 一处写完：

| 协议 | 正文 |
|---|---|
| `openai-completions` | `{ model, stream: true, stream_options: { include_usage: true }, messages: [{ role: 'user', content }] }` |
| `openai-responses` | `{ model, stream: true, stream_options: { include_usage: true }, input: [{ role: 'user', content }] }` |
| `anthropic-messages` | `{ model, max_tokens?, stream: true, messages: [{ role: 'user', content }] }` |

四条规则值得单独解释：

**流式写在正文里，不写在头上。** 三种协议都靠 `stream: true` 表达这件事，上游也只认这个字段（Anthropic 同样是给了 `stream` 才回 SSE）。

**诊断只发流式请求，没有「非流式」这一种。** 整包响应里既没有「首字节」这个时刻（§3.3），也拿不到上游的用量（用量挂在 SSE 的收尾帧上，§3.4）。一次非流式诊断跑完，表里半列都是 `—`，那不是「这次没测到」，而是「这种请求方式压根测不出来」。所以它不是一个可选模式，是一个缺省。

**两个 OpenAI 协议必须自己写 `stream_options.include_usage`。** 代理层的 `openai-completions` 原生适配器会补这个字段，但 `OpenAiResponsesNativeAdapter` 有意原样透传正文，`applyOpenAiResponsesRequestDefaults` 在真实链路上没有调用点。诊断不能指望某个下游顺带补上：不写，收尾帧里就没有 `usage`，输出 Token 恒为 `—`。Anthropic 没有这个概念，不写。

**`max_tokens` 只在直连 Anthropic 时出现。** `/v1/messages` 把 `max_tokens` 当必填，不给就是 400；而转换层在不给时会补一个 4096 的上限——一条「Hi」理论上有成本风险。所以流式诊断压到 16（只要一个字节就能量到首字），速度诊断放大到 512（数完 1 到 200；16 个 Token 会把数数掐断，那时量到的不是出字速度而是上限速度）。

**`converted` 为真时不加输出上限。** 被协议转换改写过的目标多是 OpenAI 形态，而 OpenAI 的 o 系模型只认 `max_completion_tokens`，塞 `max_tokens` 反而换来一个 400。

### 3.2 两种模式

| 模式 | 形态 | 提示词默认值 | 量什么 |
|---|---|---|---|
| `streaming` | SSE | `Hi` | 首字延迟、耗时、用量、输出速度 |
| `speed` | SSE | 数 1 到 200 | 输出速度、首字延迟、耗时、用量 |

两种模式**只有提示词不同**，请求写法完全一样：都给 `stream: true`，都要用量。「测速度」不是「连通性 + 多测几个数」，而是同一台机器上换一段更长的正文——多轮汇总、指标口径、失败判定全部共用一套代码，两条路径之间不存在「只有一边会犯的错」。

**速度是派生值，不是「速度模式才量得到的量」。** `outputTokens ÷ 耗时` 两个操作数在任何模式下都拿得到，所以 `streaming` 也会算输出速度；拿不到输出 Token 或本轮失败时才是 `null`（「没有速度」与「速度为零」是两件事）。两种模式的区别在于**分母里首字等待占多大比重**：`streaming` 只让上游生成一个词，比值基本等于「首字延迟的倒数」；`speed` 让上游连续生成数百个 Token，比值才接近稳态出字速度。因此界面两种模式的读数都如实展示，不因为「这不是速度模式」就把数字抹掉——抹掉会让用户以为渠道没给速度，而这恰恰是 `streaming` 模式最常被误读的地方。

唯一的例外是草稿连接测试（§2）：它用 `DiagnosticBodyOptions.stream: false` 显式要整包正文。那个探针是一问一答的握手，用 `requestHttpBuffered` 发一次、只看状态码，压根不读流；让它收 SSE 只会把「握手多久」量成「整条流多久」。这个开关是给那一个调用点的，不是给用户选的模式。

### 3.3 首字延迟（TTFT）

记的是**第一段真实生成内容到达的时刻**，不是第一块字节。上游先回一帧 role、再回一帧用量，都不是用户看到的字；按字节打点会让同一个渠道在诊断面板里的首字比观测页上低一截。口径与 `proxy/observers/attempt-observer.ts` 一致。

上游一个真实内容都没给过时是 `null`——没测到不是测得 0。

形态对不对（上游到底有没有按 SSE 分帧）不在这里判：那是执行器的职责，上游回整包时这次尝试会被直接判成失败。因此「测得出首字」本身就意味着帧真的是逐块到的。

### 3.4 用量

三种协议的字段名不同，但都只给「输入 / 输出」两个数。因为诊断恒为流式，用量**只有一个来源**：`StreamProbeResponse` 里的那个累加器，与 `proxy/observers/usage/` 同一口径。有些网关在同一个 `usage` 里既给 Chat 风格字段（占位 0）又给 Responses 风格字段（真实值），按顺序取「第一个数字」会先撞上占位 0，所以优先取正数，一个都没有时才回落到 0。

这条口径现在只在 `probe-response.ts` 存在一份：原先整包形态要另走 `readUsage` 从响应正文里抠数字，两条读法各有各的边界，同一次诊断换个模式就可能给出两个数。恒走流式之后那个分支没有调用点，已经移除。

不该拿到用量的时候它会是空：请求里没写 `stream_options.include_usage`（§3.1）、或者上游压根不认这个字段。**丢字段是上游的自由，我们只负责把话说清楚**——请求里写了，收尾帧里还是没有，那就是这个渠道不报用量。

读不到就是 `null`。诊断面板宁可显示 `—`，也不编一个 0 出来。

缓存命中（`cachedInputTokens`）也走同一个来源。它是**输入的子集**，不是一个额外字段：有的渠道把它挂在 `prompt_tokens_details.cached_tokens`，有的用 Anthropic 的 `cache_read_input_tokens`，认名字的活全部交给累加器，`usage()` 只负责原样透出。这个数在三处被丢掉过一次（`usage()` 只取输入/输出、逐轮结果没有这个字段、汇总不计算），结果是界面上根本无从回答「提示词缓存到底有没有被用上」。口径见 §6.3。

### 3.5 输入长度

「输入长度」量的是**长上下文下的链路表现**（预填充耗时、网关缓冲），所以补齐用的是中性的填充句子而不是重复同一个字符：多数网关会把重复字符压掉，那样长度就白加了。用一句固定英文而不是随机串，是为了让同一组配置在不同渠道之间可比。

只补不截：用户写的提示词已经超过目标长度时，尊重他写的那份。

## 4. 可测目标的规划

`planDiagnosticTargets` 是渠道诊断里唯一读库的地方。它回答的是「用户当下保存的那一份配置意味着哪些可测目标」。

「可测」的判定与界面侧一致：模型已启用、这个协议有原生端点或有可转换的端点。一个模型在同一协议上可能既有原生端点又有转换路径，此时**原生优先**——那才是用户配的那条链路，转换只是可用的替代。

端点 URL 为空时借用供应商级配置，与真实请求的唯一区别就在这里，所以补齐后交给规划器，不自己拼字段。

**两层都没配地址时不为每一轮都发一次。** 同一个配置每一轮都会得到同样的结论，重复 N 次只是把同一个错误抄 N 遍。

## 5. 参数分层与取值边界

诊断有四个参数，其中三个随载荷走，一个由 kind 声明：

| 参数 | 归哪一层 | 作用范围 |
|---|---|---|
| 模式 | 载荷（`ModelTestTaskItem`） | 这一次任务的写法 |
| 轮次 | 载荷 | 这一个目标的重复次数 |
| 提示词 | 载荷 | 这一次任务的正文 |
| 输入长度 | 载荷 | 这一次任务的正文 |
| 并发 | **kind 的注册信息** | 同一个 kind 同时在飞几个请求 |

前四个随入队一起下发，不写任何配置。**并发不逐次下发**：它决定的是「上游读数会不会被稀释」，那是调度属性，属于 kind（诊断声明为 1，见 [task-queue.md](../overview/task-queue.md) §4.1），不该由界面每次替它拍板。

**但「不进服务端配置」不等于「不记」。** 轮次 / 输入长度 / 提示词作为**草稿**存在界面的 `localStorage` 里（`store/model-test-config`，键名 `osw-model-test-config`），关掉面板再打开还在，否则每回诊断都要从 1 轮重新填一遍。存本地而不是存 `settings` 是有意的：这是「这台机器上这个人习惯怎么测」，换台机器重新来一遍是对的，跟着云同步走反而多出一份谁也没答应的状态。服务端仍是每批载荷说什么就测什么，它不读这份草稿。

这条分层（载荷 / kind 声明 / 本机草稿）与 §5.1 的「不设上界」互相独立：存到哪里都不该顺手加上界。

### 5.1 只保留下界，不给上界

轮次的下界是 1，输入长度的下界是 0。这是**定义**不是策略：诊断至少要问一次上游，零轮不是一个有意义的请求；负长度不是一个长度。

上界刻意不给。多跑几轮花的是用户自己的钱、等的是用户自己的时间，把提示词补到几十万字同样是他的账单和他的等待——替他判断「测到多少算够」没有任何依据。界面上那句「不设上限」的注释就是这条决定本身，不是漏写。

同理，契约里 `rounds` 只有 `.min(1)`、`inputLength` 只有 `.min(0)`，没有 `.max()`。以后也不要加：加的那一刻就等于宣布「我们比用户更清楚他要用多少」。

并发同样不设上限。kind 声明多少就同时飞多少——要的是最快跑完，拦住只会让人以为界面卡了。并发不合法（非正数、非有限值）时按 1 处理。

### 5.2 默认值是契约的一部分

`ModelTestTaskItemSchema` 里的 `default()` 不是服务端的宽容。入队载荷少了某个字段时，语义必须仍然是「按最朴素的方式测一次」；否则升级服务端会让旧调用方悄悄换一套测法，而他们看不到任何变化。

`mode` 的默认值是 `streaming`，不是「什么都不测」：诊断只有两种测法，而少给一个字段的调用方要的显然是「测一下通不通」——那就给结论最全的那一种。这也是模式被砍到两个之后默认值唯一站得住的选择：旧的 `connectivity` 已经不是合法值了，任何还想按老写法跑的调用方都会在解析阶段就被挡住，而不是被悄悄降级成另一种测法。

## 6. 多轮汇总口径

多轮明细在 `rounds` 里，顶层那一行是汇总。汇总是**一次诊断结论的唯一定义处**（`summarizeRounds`），界面不重新计算——否则同一条结论在服务端日志和面板上会有两个数。

| 字段 | 口径 |
|---|---|
| `success` | 全部通过才算通过 |
| `statusCode` | 取**第一个失败轮**的码；全通过时取最后一轮的 |
| `errorMessage` | 取第一个失败轮的原话 |
| `durationMilliseconds` | 各轮均值，四舍五入到整数 |
| `ttftMilliseconds` | 各轮有效值均值；一个有效值都没有时 `null` |
| `tokensPerSecond` | 各轮有效值均值，**保留两位小数** |
| `inputTokens` / `outputTokens` | 各轮有效值均值，四舍五入到整数；一个有效值都没有时 `null` |
| `cachedInputTokens` | 各轮有效值均值，四舍五入到整数；一个有效值都没有时 `null` |

三条理由：

**为什么 `success` 要「全部通过」。** 跑三轮挂一轮仍然要红。否则「稳定通过」和「碰巧过一次」在界面上长得一模一样，而这个区别恰恰是用户最想知道的。

**为什么状态码取第一个失败轮。** 查错要看的是失败那次的 HTTP 码，不是最后一轮碰巧的 200。同理错误原文取第一个失败的。

**为什么速度保留两位小数。** `formatOutputSpeed` 不负责截位，多轮均值会给出 `12.3456789` 这种在界面上毫无意义的精度。

### 6.1 `null` 不等于 `0`

`null` 表示**没测到**，`undefined` 表示**这一轮没有这个字段**。两者都不等于 `0`：上游没报用量，与真的产出了零个 Token，是两件事。混成一个数会把「未知」摊进「零」的口径里，之后任何按 `0` 做的统计都会被污染。

这条在流式诊断里尤其重要：首字没测到时是 `null`，不是 `0`——`0` 会读成「瞬间出字」。

速度同理。没有输出 Token 就是没有分子，耗时不正说明这次尝试根本没有可度量的时长，两种都返回 `null`。**「没有速度」与「速度为零」是两件事。**

### 6.2 速度公式的分母是整段尝试耗时

速度 = 输出 Token ÷ 尝试耗时，分子分母来自同一批样本。

看起来更贴切的「输出 Token ÷ 出字时段」会算出不可能的数值，而且错的不只是边界情形：上游报的输出 Token **包含推理 Token**，而推理 Token 恰恰是在首字延迟那段时间里产出的。挖掉这段时间、留下那些 Token，分子分母就不同源了——一次思考 8 秒出 8000 个推理 Token、再 2 秒出 200 个正文 Token 的尝试，会显示成 4100 TPS。那不是采集误差，是公式本身算错了。完整推导见 `packages/contracts/source/metrics.ts` 的 `tokensPerSecondFromTotals` 注释。

代价是语义：得到的是**端到端出字速度**，包含首字等待。首字慢的模型 TPS 更低——但那正是用户实际感受到的速度，而「多久开始出字」由首字延迟单独回答，两个维度并没有被合并。

### 6.3 缓存命中率：`cachedInputTokens ÷ inputTokens`

命中率回答的是「这个渠道的提示词缓存到底有没有被用上」——一个判断，不是一笔用量。它不出现在逐轮表里（那是每轮的 Token 明细），也不在结果行里，所以只在汇总区出现一次。

- 分子 `cachedInputTokens` 是分母 `inputTokens` 的**子集**，不是另一笔要相加的输入。
- 两个均值取自**同一批轮次**。分子分母各取各的轮次，算出来的比率不属于任何一次真实请求。
- 比率本身由 `@common/metrics` 的 `cacheHitRate` 现算，与请求详情、总览页同一个定义；界面用的也是同一个 `formatPercent`（一位小数）。
- 任一值为 `null`（上游压根没报缓存字段）时界面写 `—`，**不能算成 `0%`**：`0%` 是「这次一次都没命中」的说法，与「不知道」必须分开。

## 7. 记账与遥测

### 7.1 请求观测

渠道诊断的每一次探测都是一次**内部执行**（`origin: 'internal'`）：请求日志、尝试记录、用量都按真实请求落库，`logicalModelId` 是 `diagnostic`。这样「诊断通过但真实请求失败」能被追出来——两者的记录在同一条链路上。

草稿连接测试不做这些（见 §2）。

### 7.2 遥测

`provider_tested` 在**每个被测目标收尾处**发一条，`result` 说的是这一个目标的成败。

队列里一条任务就是一个「供应商 × 模型 × 协议」，所以一次「全测」会产出多条事件，而不是一条汇总。同一批里既有 `success` 也有 `failed` 是正常现象，「测试了几次」只能按事件条数读，不能按用户点了几次按钮读。

**被取消的那次不发。** 它没有结论，记成失败会把「用户点了取消」算进失败率里。0 条结果时同样不发。详见 [telemetry.md](./telemetry.md) §3。

## 8. 交付、取消与重测

### 8.1 交付：交给服务端队列

界面不再持有队列。选中项与参数拼成一批 `ModelTestTaskItem`，一次 `POST /api/tasks/enqueue` 交出去；之后界面只订阅 `/api/tasks/stream`，把任务按 `key` 叠到本地计划表上。键由契约层的 `modelTestTaskKeyOf` **唯一构造与解析**（`@common/diagnostics`），内容是 `模型 id + 协议 + mode + rounds + inputLength`：服务端写键与界面读键共用同一份实现，格式漂移会变成编译期错误。状态、并发、去重、取消的细节在 [task-queue.md](../overview/task-queue.md)。

这样分的理由是那四件事本来就不属于某一个组件：并发与收尾是队列语义，和渲染周期无关；每个任务都是一次真实的上游请求、真金白银，它需要能在**没有 React 环境**下被测；面板关掉再打开、切页再回来，队列本身不该跟着重建。**面板卸载不再掐掉在飞的任务**——用户离开的只是那块界面，不是他自己点下去的那一批。

### 8.2 并发

kind 声明为 **1（串行）**：诊断量的是延迟与首字，同时打多个上游会互相污染读数。引擎保证「任何时刻在飞数恰好等于上限」，见 [task-queue.md](../overview/task-queue.md) §4.1。

### 8.3 取消

取消的语义是「不再继续花钱」，不是「把手上这个做完」。按 `taskId` 取消：**未开跑的直接出队，零上游请求**；在跑的随 `AbortSignal` 在**步边界**收（kind 在每一轮开始前检查信号）。

**取消不是失败。** 结局是 `cancelled` 而不是 `failed`，错误文案不写，遥测不发（§7.2）。被取消的那一轮不计入结论。

关闭面板时先确认，确认后按 `kind` 取消这一批；**最小化不取消**，收起来只是少占地方。

### 8.4 连点两下

去重在服务端：同 kind 同 `keyOf`（同一目标、同一套测法参数）已在排队 / 运行中时不会重复入队，第二次点击的那些项被算作 `skipped`。防的就是一次真实的双倍计费。键里带着 `mode` / `rounds` / `inputLength`，所以「同一目标换了参数重测」是一个新任务，不会被当成重复项静默跳过。

### 8.5 重测

重测不重新规划：直接拿表里失败的那几行，按当前参数重新入队（键由 `modelTestTaskKeyOf` 给出；参数没变就命中同一行，变了自己是另一行）。其它行的结论原样保留，不整表重建——用户点「重测失败的」就是想看那几行变了没有，而不是想看一张新表。

## 9. 测试策略

## 10. 验收

- 渠道诊断与草稿连接测试的行为差异与 §2 表格逐条一致（尤其是草稿那次不写库、不进冷却）。
- 渠道诊断发出去的每一次请求都是流式：正文里有 `stream: true`，两个 OpenAI 协议还带 `stream_options.include_usage`；请求头 `accept` 是 `text/event-stream`。契约里不存在能被解析成「非流式诊断」的值。
- 任何一条诊断结论里，首字、耗时、用量、速度都来自同一次流式尝试，不存在「整包正文 + 流式打点」这种混搭。
- `rounds`、`inputLength`、并发在任何一层都没有上界；只有下界。
- 所有「读不到」的量都是 `null`，界面上显示 `—`，没有任何一处把未知写成 `0`。
- 多轮里有一轮失败时，顶层是失败、状态码是第一个失败轮的码。
- 取消之后没有 `failed` 的行、没有遥测事件；未开跑的那几项零上游请求。
- 连点两下只发出一批请求（同键去重）。
- 面板卸载 / 切页不中断在跑的任务；关闭面板才会取消。
- 界面不重新计算任何汇总字段，只渲染服务端给的结论。
