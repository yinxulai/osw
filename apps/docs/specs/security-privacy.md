# 安全与隐私

## 安全边界

### 网络隔离

- 服务默认绑定本机回环地址 `127.0.0.1`，默认不暴露到局域网
- `listenHost` 可由用户在设置中修改；支持改为 `0.0.0.0` / `::` 绑定所有网卡以暴露给局域网 / WSL / 容器，属于用户显式选择，用户需自行依赖操作系统防火墙控制入站访问
- 管理接口校验 `Host` 头必须是回环地址（`127.0.0.1` / `localhost` / `[::1]`），否则一律 `403`。这一条挡的是 DNS rebinding：攻击者把域名解析到 `127.0.0.1` 之后，浏览器认为请求与目标同源、CORS 直接失效，此时只有 `Host` 还能说明「这条请求是奔着谁来的」
  - 校验发生在**静态托管之前**：控制台页面与 API 同端口，先把页面发出去就等于先把「被 rebinding 的域名加载了这个页面」这件事做完了
- 代理入口（`/v1/*`）不校验 `Host`：它面向的是任意调用方，回环 `Host` 校验只会挡住正常用途，那里的边界是「监听在哪里」

### 访问控制

管理接口与代理入口是两套边界，不能混为一谈：

- **代理入口**（`/v1/*` 等）：面向用户的调用方，**不校验调用方身份**。本软件不向下签发任何调用方 API Key——客户端在 `Authorization` / `x-api-key` 里填什么都不影响能不能调通：那些头只会被脱敏后写进日志，并在转发时换成渠道自己的密钥（见下方「密钥存储」）。因此「谁能用这个代理」完全由**它监听在哪里**决定：
  - 监听在回环（默认 `127.0.0.1`）时，本机任意进程与任意网页都能调它——同源策略只挡「读响应」、不挡「发请求」；
  - `listenHost` 改成 `0.0.0.0` / `::` 时，同网段任何设备都能调它，直接消耗用户的渠道额度；
  - 要不要向下签发调用方 API Key 属于未完成项，见 [roadmap.md](./roadmap.md) §7。
- **管理接口**（`/api/*`）：只服务于本进程自己的控制台与命令行，**每次应用启动随机生成一份凭证**（`management/token.ts`），请求必须带上 `x-osw-token`，否则 `401`。
  - 凭证是 32 字节随机数的 base64url。**由宿主（桌面主进程 / 命令行进程）在应用启动时生成一次**，经 `RuntimeConfig.managementToken` 交给 core；core 只负责落盘与校验，自己不生成——因为 core 的 `startServer()` 不等于一次应用启动：桌面形态的服务跑在独立进程里，崩溃后会被宿主重启（`server-host.ts` 的重启预算），若凭证跟着它重算，主进程手里那份立刻作废，渲染层随后的每次请求都会 `401`。同理，它与代理是否启动无关。
  - 落盘在 `<dataDir>/management.token`（`0600`），退出时删除。它不进 `runtime.json`——那份快照是「谁在跑」的描述，会被 `status` / `stop` 之类的外部进程读，凭证没有理由跟着出去。
  - 比较走 `crypto.timingSafeEqual`（长度先比一次，长度是固定值，从协议文档就能知道，不构成泄露）。
  - 为什么需要它：**「只监听回环」不是访问控制**。本机任意网页都能向 `127.0.0.1` 发请求，`Content-Type: text/plain` 的「简单请求」甚至不会被预检拦住，于是 `/api/provider/export`（`includeApiKeys: true`）这样的接口就是一条把明文密钥读走的通路。凭证只存在于本次启动的自家进程之间，页面猜不到。
  - 管理接口固定监听回环（`managementHost` 由宿主固定为 `127.0.0.1`，没有对用户暴露的开关，CLI 的 `--host` 只作用于代理）。
- **凭证怎么到页面**：桌面形态由主进程通过 preload 注入（`window.__OSW__.apiToken`，主进程自己就是生成方，不靠服务回报）；命令行 `--web` 形态下页面本来就是管理服务自己发的，入口 HTML 在被送出时被注入同一行脚本（`management/core/static-web.ts`，入口文件带 `no-cache`，不会被缓存下来）。两种形态都不写 `localStorage`：凭证每次启动都会变，缓存一份只会让下一次启动读到废值。
  - **例外**：`pnpm dev:preview` 直接在浏览器里开 Vite 产物，等不到宿主注入，因此拿不到凭证——那条通路的 API 调用一律 `401`，只适合看静态界面。开发期要看完整功能请用 `pnpm dev`（Electron），或 `pnpm build:cli && pnpm start:cli`（命令行托管）。
- **跨域**：管理接口只回显**已识别的本地来源**的 `Access-Control-Allow-Origin`（`Origin: null` 的 `file://` 渲染进程与 loopback 上的来源），名单外的来源一个 CORS 头都拿不到，预检阶段就被浏览器挡回。
  - 允许的请求头是 `Content-Type, X-OSW-Token`（凭证头漏了它，每条带凭证的跨源请求都会卡在预检上）；允许的方法是 `POST, OPTIONS`（`/api/*` 全部是 POST，`GET` 一律 `405`）。
  - 预检在凭证检查**之前**短路成 `204`：预检是浏览器自己发的，它既不可能带自定义头，也不该被要求带。
  - 这张名单**不是防线**，只是让正常形态（开发期控制台在 Vite server 上、桌面形态在 `file://` 上）能跨源到达自己进程的管理服务。真正的边界是回环监听、Host 校验与本次启动的凭证。

### 单实例

- 桌面、命令行、容器三种形态都只允许一个实例持有同一个数据目录；互斥由 core 的 `runtime/instance-lock.ts` 提供，属于**基本能力**，不是某个宿主的补丁：
  - 锁文件是数据目录下的 `instance.lock`，记录持有者 pid、启动时间与心跳时间；
  - 判定持有者是否活着，既看 pid 还在不在，也看心跳新不新鲜，因此 pid 被操作系统复用不会把死实例误判成活实例；
  - 心跳由 `startInstanceLockHeartbeat` 周期续写，宿主崩溃后残留的锁会被下一个实例判定为遗弃并接管；
  - 换端口换不掉它：锁挂在数据目录上，不在端口上。
- 桌面形态在这之上还有一层操作系统级的 `app.requestSingleInstanceLock()`：第二次启动不新开进程，而是把已有窗口唤到前台。

### 路由脚本沙箱

路由工作台的 JS 脚本节点在服务端进程内的 `node:vm` 沙箱里执行用户源码，边界如下：

- 沙箱里只有三样东西：`payload`（本次运行 payload 的**深拷贝**）、`get(路径)`（只读取值）与 `console`（日志回传 trace）；
- 没有 `require` / `import` / `eval` / `Function`：`codeGeneration.strings = false`，脚本无法再生成新代码；
- 没有网络与文件系统 API：沙箱不注入任何宿主对象，脚本只能操作内存里的那份数据；
- 有限时：节点可配超时（上限 10s），超时即中断并把失败原因写进 trace；
- 脚本改动不会污染引擎正在使用的决策数据（传的是深拷贝），失败也不阻断整张图执行；
- 脚本内容属于用户配置，随工作流图的版本一起保存在本地，不随请求日志外发（规则模式没有脚本节点）。

### 路由 LLM 节点的出站调用

路由工作台的 LLM 节点会发起真实上游请求，因此：

- 调用**复用逻辑模型自己的上游通路**（供应商、协议、密钥、故障转移），不新增密钥存储位置，密钥仍在主进程 / 密钥环里，不进渲染进程；
- 提示词与回复只在本地参与运行时数据，写回 payload 的只是回复文本；
- 出站请求路径与普通代理请求一致，同样受出站代理设置与日志脱敏规则约束，详见 [outbound-proxy.md](./outbound-proxy.md)。

## 密钥存储

- Provider API Key 不写入明文配置、日志或导出的供应商包（除非用户显式选择包含）
- Provider API Key 使用 Electron `safeStorage` 或系统密钥环（macOS Keychain / Windows Credential Manager / Linux Secret Service）存储
- 数据库中仅保存 Provider API Key 的密钥引用 ID
- 供应商包默认导出脱敏版本（不含明文 API Key）；包含明文必须由用户显式勾选，并在界面提示该文件等同于凭据，详见 [provider-model.md](./provider-model.md)
- 自定义上游代理 URL 例外：允许携带账号密码，并作为普通设置写入 SQLite；代理设置不进入供应商包，日志、错误与测试结果仍必须脱敏，详见 [outbound-proxy.md](./outbound-proxy.md)
- 云同步的凭据（Gist 上是 GitHub 令牌）与 Provider API Key 同一套设施：只存进宿主密钥库，按后端各存一份且引用固定，不写入 SQLite、日志或任何导出文件；数据库里只留当前承载方式、账号名、远端句柄与两个同步时间戳，详见 [cloud-sync.md](./cloud-sync.md)

## 隐私策略

### 遥测

- 使用统计**默认开启**：匿名上报统计数据用于改进功能，界面上不提供任何入口（不设开关、不设设置模块、也不做提示）；完整口径（事件白名单、匿名标识、上报链路）见 [telemetry.md](./telemetry.md)（口述口径见 §3，自查走管理接口的预览）
- 统计链路是**唯一**被允许出站的非模型流量：它直连自建端点，不在客户端直接打到任何第三方分析服务，也不走用户的出站代理设置
- 除它之外不存在任何形式的遥测：没有崩溃上报、没有行为埋点、没有远程配置拉取

### 数据本地化

- 所有配置、密钥、日志保存在用户主目录下的隐藏目录，位置不随平台变化
- 不向任何第三方服务器上传用户数据；唯一例外是默认开启的匿名使用统计，它不携带任何用户内容（见 [telemetry.md](./telemetry.md)）。统计只发固定枚举、布尔与分桶，没有任何位置能随手塞进一段内容——**包括模型名在内**（理由见 [telemetry.md](./telemetry.md) §3）；其中关于「处理了多少任务」的那一条只报「成功处理了一次」，不带任何属性，也不含耗时、Token 或状态码
- 配置云同步是用户主动触发的例外：数据发往**用户自己的**第三方云存储（当前是 GitHub Gist），由他本机直连完成，我们不参与也不中转（同一条判断见 [outbound-proxy.md](./outbound-proxy.md) 对统计链路的说明）。快照整份只做 base64 编码，**这是编码不是加密**，而快照里带着各供应商的 API Key——「换台机器拉一次就能用」正是靠这一点成立。同时这种「私密 Gist」也不是加密存储：GitHub 及其运维方在技术上能读到内容。因此这条通路的定位是「用户自己信任的容器」，不是安全的密钥仓库，这一点在各处文档里写明（见 [cloud-sync.md](./cloud-sync.md)）
- 代理仅转发用户请求到用户配置的 Provider 供应商

### 请求与响应数据

- 默认保存完整请求体和响应体，以便直接进行请求调试和故障分析；用户可在设置中关闭正文记录
- 日志同时记录元数据：时间、模型、协议、供应商、状态码、耗时、错误摘要
- 客户端请求、最终响应、每次 Provider 尝试，以及协议转换前后的内容均视为敏感本地数据
- 记录前必须脱敏 Authorization、API Key、Cookie、Set-Cookie 等敏感头；正文内容完整保存在本地数据库，正文自身不视为已脱敏
- 请求与响应都**不设大小上限**：能通过守卫调用管理接口的一方本来就能改配置、导出密钥（凭证见「访问控制」），给它再插一道大小闸门挡不住任何我们假定可信的人；代理接口拒「大正文」等于替用户决定他的多模态请求能有多大，`core-network` 的缓冲取正文也一并去掉了那个上限参数。代价要说清楚：正文会完整读进内存并落库，内存与本地存储占用随请求量增长；这是本地工具的自担选择，不做资源消耗攻击假设（同一条判断见 [request-rewrite-rules.md](./request-rewrite-rules.md)）
- 采集与保留是两个独立维度：请求日志与请求响应正文各有一个开关、各有一个自动保留天数（请求日志默认**永久保留**，正文默认 **7 天**）；关闭开关只影响后续采集，不删除已有数据
- 清理分两种粒度：按请求日志保留天数清理会级联删除该请求的正文、尝试记录与用量行；只按正文保留天数清理则只删除正文（含协议转换前后两个视角），请求行、尝试行与指标保留，历史统计不失真
- 手动“清理历史日志”支持分别输入两个保留天数后即刻执行，不改动自动保留设置
- 内容查看和导出都应明确提示可能包含提示词、文件内容和模型输出；导出默认不包含正文
- 日志内容只保存在本地数据目录，不上传任何第三方服务器

## 本地数据位置

数据目录是 `<用户主目录>/.osw`（开发档 `.osw-development`），三个平台同一规则，见 [packaging.md](./packaging.md) §5.5：

| 文件 | 内容 | 丢了会怎样 |
|------|------|------|
| `config-v1.db` | 供应商、模型、路由、改写规则等用户配置 | 不可再生，**值得单独备份** |
| `data-v1.db` | 请求日志、正文、用量、运行时日志与健康状态 | 只丢历史统计，代理照常工作 |
| `secrets.json` | 桌面形态的 API Key 密文与主密钥（主密钥也可放系统钥匙串） | 需要重新录入 API Key |
| `secrets.cli.json` / `secrets.cli.key` | 命令行形态的密钥文件 | 同上 |
| `telemetry-id` | 匿名使用统计的本地安装标识（仅在开启统计后生成） | 等同于换一台新设备，统计上重新计数（见 [telemetry.md](./telemetry.md) §4） |

两个数据库文件的职责边界与分库理由见 [data-model.md](./data-model.md) §2.1。两个形态的密钥文件刻意不同名：密文算法不同，同名同址会让后写的那个把前一份条目全部作废（见 [packaging.md](./packaging.md) §5.1）。想只保留配置、清空历史，删掉 `data-*.db` 即可——下次启动会重建一个空文件。
