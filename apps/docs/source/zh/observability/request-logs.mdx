# 请求记录

**请求记录**页按时间倒序列出每一条经过本服务的请求，是排查「为什么这次没跑通」的第一现场。

## 列表能看到什么

- **来源渠道**：请求带的模型名来自哪个客户端。
- **路由结果**：落到了哪个[逻辑模型](/upstreams/logical-models)。
- **状态与耗时**：是否成功、端到端耗时。
- **协议与流式**：请求用的协议、是否流式。
- **Token 用量**：输入 / 输出 token。

## 尝试明细

一条请求可能尝试过多个候选。每条记录都能展开出**逐次尝试**：每次试了哪个供应商 / 模型、结果如何、失败原因是什么。

失败原因会归类展示：

| 归类 | 含义 |
| --- | --- |
| 超时 | 连接或空闲超时。 |
| 限流 | 上游返回 `429`。 |
| 服务端错误 | 上游 `5xx`。 |
| 鉴权失败 | 上游 `401` / `403`。 |
| 其它 | 其余情况。 |

这也是理解[故障转移](/upstreams/failover)到底做了什么的最直接方式。

## 内容捕获

请求体与响应体内容默认**被记录**，可在**设置 → 数据 → 请求日志**里调整：

| 设置项 | 说明 |
| --- | --- |
| 记录请求日志 | 总开关。 |
| 请求记录保留策略 | 请求**元数据**保留多久（默认永久）。 |
| 请求内容保留策略 | 请求 / 响应**正文**保留多久（默认 7 天）。 |
| 敏感请求头脱敏 | `authorization`、`x-api-key`、`cookie` 等默认不落库。 |

<Callout title="请求体不脱敏" type="warning">
敏感**请求头**会被脱敏，但请求**体**不会：提示词、代码、工具输出都会按原样存下来。处理敏感数据前先想清楚这一点。
</Callout>

<Callout title="捕获不限制大小" type="info">
请求体会被完整读进内存后再落库，不设大小上限。超大请求体会占用相应内存。
</Callout>

## 清理

请求记录里可以手动清理，也可以让保留策略自动过期。存储位置见[数据目录与保留](/observability/data)。
