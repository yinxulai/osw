# 统计分析

**统计分析**页把请求记录聚合起来看趋势，回答「这段时间整体跑得怎么样」。

![OSW「统计分析」页：把请求记录聚合成请求量、成功率、耗时、Token 用量与故障转移趋势。](/screenshots/zh-CN/light/analytics.png)

## 指标概览

页顶的四张卡片是这段时间的**总体结论**：总请求数、成功率、缓存命中率与 Token 消耗；右上角切换统计范围（如近 7 天）。

![OSW「统计分析」页顶部指标概览：总请求数、成功率、缓存命中率与 Token 消耗。](/screenshots/zh-CN/light/analytics-stats.png)

## 用量分布

**用量分布**把请求量按时段摊开（热力图或柱状图可切换），一眼看出高峰在哪、哪段时间几乎没流量。用它交叉验证成本与限流问题：某个供应商的限流是不是总发生在你的高峰时段。

![OSW「统计分析」页的用量分布卡片：按小时铺开的热力图，右下角是「少 → 多」的图例。](/screenshots/zh-CN/light/analytics-usage.png)

## 看什么

| 维度 | 用途 |
| --- | --- |
| 请求量 | 用在哪些模型、哪个客户端在用。 |
| 成功率 | 整体是否稳定。 |
| 耗时分布 | 响应是否变慢，慢在哪一段。 |
| Token 用量 | 用在哪个逻辑模型、哪个渠道上最多。 |
| 故障转移频次 | 哪个供应商在反复掉链子。 |
| 失败原因分布 | 超时 / 限流 / 5xx / 鉴权各自的占比。 |

## 与请求记录的分工

- **请求记录**是**逐条**的，用来定位**某一次**请求发生了什么。
- **统计分析**是**聚合**的，用来发现**一段时间**里的模式。

<Callout title="分析的是你自己的请求" type="note">
这里的统计只来自本机的请求记录，与匿名使用统计是两回事。后者见[本地优先与密钥](/observability/privacy)。
</Callout>

## 排障思路

结合故障转移看，典型判断：

- 某供应商失败率突增 → 去看它的冷却记录与[渠道诊断](/upstreams/providers)。
- 成功率不低但耗时上升 → 可能是某条慢候选把整体拉高，考虑调队列顺序。
- Token 用量异常 → 去[缓存亲和](/upstreams/cache-affinity)确认提示词缓存是否还在命中。
