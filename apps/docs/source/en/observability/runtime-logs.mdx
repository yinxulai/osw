# Runtime logs

**Runtime logs** record what the **service itself** is doing, not your requests — startup and shutdown, listen-port changes, config saves, route version publishing, and internal errors and warnings.

## Toolbar

![OSW Runtime logs page toolbar: search, level filter, live-update toggle, pause, export, and clear.](/screenshots/en/light/runtime-logs.png)

- **Search**: filter log bodies by keyword.
- **Level**: show only one level (e.g. warn / error).
- **Live update**: new logs scroll in automatically, and can be **paused** at any time to avoid flooding.
- **Export**: export the current view to a file to hand to a collaborator.
- **Clear**: drop existing logs.

## Difference from request logs

| | Runtime logs | Request logs |
| --- | --- | --- |
| Subject | The service itself | The **user requests** that pass through |
| Question | Is the service working correctly | Why did this request fail |
| Typical content | Startup, config, internal errors | Dispatching, attempts, latency, upstream errors |

<Callout title="The two logs are not mixed" type="info">
Runtime logs serve troubleshooting — fields are request ID, latency, error code. Telemetry events serve product decisions and must be anonymous and low-cardinality. The requirements of the two are exactly opposite, so they are kept separate.
</Callout>

## Common uses

- Startup failure: port in use, data directory not writable.
- Config anomalies: cloud-sync conflict, key decryption failure.
- Routing issues: whether a particular publish succeeded, and whether there was a rollback.

## Retention

Runtime log retention is tuned in **Settings → Data → Log retention**. It is a **separate setting** from the request log retention policy.
