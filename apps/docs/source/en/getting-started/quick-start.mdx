# Two steps to a gateway

The first launch enters a two-step guide. It is a **straight line** — the order cannot be swapped, because each step's output is the next step's prerequisite: first decide what upstream to run requests on → then know what to fill in. There is no progress bar: the current step's name is the page title, and the next step's name is written on the bottom-right button (**Next: Point your tools here**).

<Callout title="Routing is not a step" type="note">
The guide does not make you design a routing scheme first — a default policy is already running and is good enough for a new user. The model pool and landing points stay editable on the "Smart routing" page whenever you want.
</Callout>

## Step 1: Add an upstream

The first step, "Add a model", adds your first upstream provider:

1. Pick a **preset** (presets pre-fill the base URL), or choose "Custom provider".
2. Fill in the provider name and the **API key** (leave blank for upstreams that need no auth).
3. Click **Fetch models** and tick the models you want from this provider.

After fetching, remember to tick specific models — with no models under a provider, requests have nowhere to land. For the full model-management page, see [Providers & models](/upstreams/providers).

## Step 2: Connect a client

The second step, "Point your tools here", shows the one address a client should point at. The same step embeds the **config editor** inline: pick a tool you use, then hit **Generate config** on the right of the **Config content** card header (it rewrites the config against the built-in default model) and **Save content** — **Discard edits** undoes it. For a tool not in the registry, copy that address in by hand. When a client is already installed on the machine, you can instead go to [Client configuration](/getting-started/client-config) and click **Generate & apply all**, and OSW edits that client's own config file, keeping a revertible copy of every change first.

Reference table:

| Your client | Base URL |
| --- | --- |
| OpenAI-compatible (Chat Completions / Responses) | `http://127.0.0.1:9300/v1` |
| Anthropic | `http://127.0.0.1:9300` |

<Callout title="The pitfall everyone hits" type="warning">
Anthropic clients append `/v1/messages` **themselves**, so the Base URL stops at the port. Adding an extra `/v1` makes it `/v1/v1/messages`, which the proxy does not recognize, and you get a 404.
</Callout>

The model name is up to you: `default`, or any non-empty name. OSW replaces it with the real model ID of the actually chosen channel. And if a client insists on an API key, any placeholder will do — the real secret is injected per provider.

## Verify it is connected

Whether the service is alive:

```bash
curl http://127.0.0.1:9300/v1/models
```

Send a message from your client, then go to [Request logs](/observability/request-logs): once the request shows up, you are connected.

The listen address and port are changed under **Settings → Network → Listener**; after saving, the proxy switches to the new port automatically.
